# 工作台设计与开发基线

更新时间：2026-08-09

适用模块：`/pingbiao`、`/api/evaluation-workbench` 及 `dashboard/evaluation_workbench/`

文档性质：规范、架构基线、验收基线与 AI 接力桥梁

## 0. 如何使用本文档

本文档不再记录逐次修复过程。它只回答五件事：

1. 工作台要解决什么问题，明确不做什么；
2. 当前生产设计和关键数据契约是什么；
3. 开发时必须遵守哪些约束；
4. 哪些未来改造已规划、满足什么条件才能启动；
5. 当前工作区做到哪里，下一位开发者或 AI 应从哪里继续。

信息优先级为：用户当前明确决定 > 仓库根目录 `AGENTS.md` > 本文档的有效基线 > 测试与代码注释 > 历史提交说明。若本文档与当前代码不一致，不得任选一方继续开发：先用测试、运行数据和 Git 历史确认真实状态，再修正代码或本文档。

本文档使用三种状态：

- **已实施**：当前代码存在且已有测试；是否部署以“当前接力状态”为准。
- **计划中**：已有方向和门槛，尚不能作为现行行为依赖。
- **禁止**：后续开发不得采用，除非用户明确改变基线。

任何 AI 接手本模块时，应先阅读第 1、2、4、9、10、11 节，再检查 `git status` 和相关测试。详细历史从 Git 获取，不把提交日志重新复制回本文档。

## 1. 产品目标与边界

### 1.1 目标

“工作台”是面向单人、低并发场景的招投标评审辅助模块，主要能力包括：

- 管理评标项目、招标文件/附件和多份投标文件；
- 解析文件并建立可追溯的页级文本；
- 对多份投标文件做本地候选筛查和 AI 查重复核；
- 从招标文件提取、编辑、选择并确认评审规则；
- 对每家投标文件完成审查、客观分和主观分建议；
- 按需使用本地 OCR、腾讯 OCR 和多模态模型补充图片证据；
- 提供网页、打印报告和 CSV 结果。

所有结论都是 AI 建议，最终由人工审核。准确性和可追溯性优先于 Token 节省。

### 1.2 明确不包含

- 投标文件或技术方案编写；
- 自动作出法定串标、废标或最终得分决定；
- 多用户协同、审批流或复杂权限系统；
- 常驻本地大模型、GPU 服务或向量数据库；
- 在展示层重新推导业务结论；
- 为单一项目、投标人、设备、金额、页码或年份编写生产补丁。

### 1.3 独立性

- 页面入口为 `/pingbiao`，API 前缀为 `/api/evaluation-workbench`。
- 使用独立 SQLite 数据库 `data/evaluation_workspace.db`。
- 文件位于 `data/evaluation_workspace/<project_id>/`。
- 不修改 `/bijiao`、`/api/compare` 的既有语义。
- 修改任何既有 API 路径、参数、字段、状态码、认证或跨域行为前，必须验证 `rokid_glasses_app` 兼容性。
- 项目删除会删除该项目数据库记录、上传文件、解析缓存和结果；仅在无运行/排队任务且用户确认后执行。

## 2. 不可违反的工程原则

### 2.1 固定优先级

**准确性与可追溯性 > 稳定性 > 效率 > Token 节省 > 展示便利性。**

性能优化不得减少全文覆盖、规则覆盖、关键证据页、异常恢复或人工可核验信息。无法证明不劣于基线的优化只能处于影子观测或默认关闭状态。

### 2.2 通用、治本、确定性优先

- 禁止将具体项目名、投标人、设备、金额、地区、页码、年份、错误句子写入生产判断逻辑或默认提示词。
- 禁止采用“发现一个错误，就追加一段提示词、一个正则或一个展示兜底”的方式持续修补。
- 修复前必须定位问题最早出现的层：文件解析、条款识别、规则编译、证据定位、模型输出契约、证据合并、落库或展示。
- 能由本地确定性信息解决的事项，不交给模型猜测。典型包括文件哈希、规则 ID、条款 ID、页码、分值守恒、父子评分关系、启用状态、模型/提示词/代码版本和证据来源。
- 正则只允许承担结构识别、格式校验和候选召回，不得代替开放语义判断；词表只能是稳定的通用结构词或法律政策清单，不得随着案例增长。
- 模型负责理解语义、提出证据和建议；系统负责约束输入输出、保存来源、校验结构并显式暴露不确定性。

### 2.3 修复顺序

可靠性统一遵循：**校验 → 定向重试 → 显式标记 → 最后兜底**。

- 不允许格式异常后静默生成“看起来正常”的结论。
- 不允许一个规则组失败覆盖已经成功的规则组。
- 不允许历史风险结论、候选优先级或人工选择悄悄影响新一轮独立提取/评审。
- 兜底只能降低自动化程度，不得提高风险、分数或确定性。

### 2.4 小服务器约束

目标环境为腾讯云 2 核 2 GB：

- 禁止引入重型常驻服务和无界线程/进程池；
- 工作台空闲时不运行任务、不发模型请求，本地 OCR 懒加载并在空闲后回收；
- 本地 OCR 默认全局单执行位，模型请求仅在服务商限制内动态并行；
- 所有页数、字符数、图片像素、缓存、并发和重试必须有上限；
- 新依赖必须同时验证 Docker 构建、峰值内存、Swap、冷启动和任务结束后的资源释放。

### 2.5 安全与兼容

- API Key、腾讯云密钥、Token、Cookie 和服务器凭据不得进入仓库、文档、日志和模型提示词。
- 密钥读取接口只返回“已配置”，不得回传明文或密文。
- 既有 API 优先向后兼容；新能力通过可选字段扩展，旧字段不得无提示改义。
- 历史结果保持可读；数据迁移优先新增字段、标记或适配，不静默覆盖。

### 2.6 变更分级与稳定核心保护

任何修改必须先分级，不能把业务口径变化伪装成普通修复：

| 变更级别 | 典型内容 | 开始前要求 | 文档要求 |
|---|---|---|---|
| A：业务决策 | 规则适用范围、评分含义、人工流程、默认选择 | 必须先获用户确认 | 必须更新对应基线 |
| B：核心架构 | 主流程、证据契约、缓存身份、OCR/模型路由、并发模型 | 先做方案、回退和 A/B 基线 | 必须更新架构与验收门槛 |
| C：兼容扩展 | 新增可选字段、服务商适配、报告格式 | 保持旧 API/数据可用 | 仅记录长期契约和兼容边界 |
| D：等价修复 | 不改变契约的代码错误、样式、日志、局部性能修正 | 定向测试和必要回归 | 通常不写本文档 |

第 3.4 节列出的稳定核心原则上不改动。确需调整时，必须说明“为什么现有核心无法满足需求、影响哪些契约、如何回退、用什么数据证明不衰减”，并在修改前更新方案、修改后更新实际状态。不得先改代码再用文档为结果背书。

### 2.7 变更闭环与评估资产

- 改动前先写清不变的业务契约、可复现样本、预期收益和可能退化的指标；不能只凭一次模型输出判断“修好了”。
- 一次修改应优先只改变一个责任层。若同时调整提示词、候选页、取证路由和结果合并，必须拆分为可独立回退、可比较的步骤。
- 用户已保存的模型、提示词、规则和历史结果不得被新默认值静默改写；任务应保留实际生效配置的版本/指纹，以便复现。
- 黄金项目和回归夹具是评估资产，不是针对某个项目写生产逻辑的理由。新增案例应抽象成可验证的通用性质，再进入测试。

## 3. 当前架构（已实施）

### 3.1 文件地图

- `dashboard/blueprints/evaluation_workbench.py`：页面与 API 边界、口令和请求校验。
- `dashboard/evaluation_workbench/storage.py`：SQLite、规则版本、任务、配置、缓存和结果持久化。
- `dashboard/evaluation_workbench/worker.py`：解析后任务、规则提取、全文扫描、综合评审、OCR/图片编排和结果归一化。
- `dashboard/evaluation_workbench/ai_gateway.py`：模型协议、请求、兼容响应和 Token 台账。
- `dashboard/evaluation_workbench/prompt_templates.py`：默认提示词及输出契约。
- `dashboard/evaluation_workbench/prompt_context.py`：提示词上下文构造。
- `dashboard/evaluation_workbench/collusion_signals.py`：查重候选与价值过滤。
- `dashboard/evaluation_workbench/ocr_gateway.py`：腾讯 OCR 能力适配。
- `dashboard/evaluation_workbench/local_ocr_gateway.py`、`rapidocr_worker.py`：RapidOCR 懒加载进程和资源回收。
- `dashboard/templates/evaluation_workbench/`、`dashboard/static/evaluation_workbench/`：独立前端和报告。
- `tests/test_evaluation_workbench.py`、`tests/test_evaluation_workbench_ai_gateway.py`：核心回归基线。

### 3.2 主工作流

1. 创建项目，上传招标文件、附件和多份投标文件。
2. 解析文件并按哈希保存页级文字与元数据。
3. 可运行多文件查重：本地生成低成本候选，AI 只复核压缩证据包。
4. 提取规则：结构定位 → 分段 AI 映射与定向补提取 → 统一编译/覆盖审计 → 一次规范化 → 确定性校验。
5. 用户编辑、勾选并确认规则集。
6. 综合评审：项目范围画像 → 投标文件全文分块扫描 → 本地确定性证据补充 → 按策略分组审查/评分 → 必要 OCR/图片增强 → 证据合并 → 重要结论提炼。
7. 页面按投标人展示审查、客观分、主观分建议并导出报告。

### 3.3 任务与并发

- 使用 SQLite 任务队列和按需 worker，不引入 Redis/Celery。
- 跨项目任务按队列执行；等待项目应显示当前运行项目及其进度。
- 单任务内部可并行不同投标人、全文页块或模型规则组，但受任务级和服务商级闸门限制；限流或过载后自动降档。
- 本地 OCR 始终受独立全局执行位约束，不能随模型并发一起放大。
- 任务允许 `partial_success`：成功单元立即持久化，失败单元可定向重跑。
- 可恢复网络错误和 HTTP 5xx/429/529 只重试当前调用；4xx 配置错误不盲目重试。

### 3.4 受保护的稳定核心

下列设计经过多轮真实项目运行，是后续优化必须保护的基础。可以重构实现，但不得在没有等价验证和回退方案时改变其行为：

| 稳定核心 | 必须保持的行为 | 允许的优化边界 |
|---|---|---|
| 模块独立 | 独立页面、API、数据库和文件目录；不影响其他模块与外部调用方 | 内部拆分、索引和样式可改，外部契约保持兼容 |
| 按需任务 | 跨项目排队、空闲退出、2 核 2 GB 下无重型常驻服务 | 可优化调度和进度，但不得产生无界并发或空闲占用 |
| 全文覆盖 | 长文件从首页到末页扫描，失败页显式进入复核 | 可改分块、索引和缓存，不能以节省 Token 为由跳页 |
| 规则提取分层 | 结构定位、AI 提取、编译/覆盖审计、一次规范化和确认前硬校验各司其职 | 可合并重复调用，不能删除来源追溯、评分守恒和补漏校验；不得按规则数量切换不同业务语义 |
| 规则版本独立 | 新一轮普通 AI 规则独立重建；人工维护内容按稳定来源保留 | 可改善条款身份，不能继承旧 AI 勾选、风险或结论 |
| 证据先于结论 | 文字、OCR、图片和本地事实保留来源、页码、覆盖与冲突 | 可正式迁移到 EvidencePack，不能用字符串覆盖或展示层重算 |
| OCR 分层 | 文字优先、本地 OCR 按需基础取证、腾讯 OCR/多模态按规则增强 | 可换适配器和候选算法，不能让所有规则默认 OCR 或用未识别推断缺失 |
| AI 建议、人工裁决 | 系统给审查和评分建议，不产生法定串标、废标、最终分 | 可改善摘要和证据，不得提高系统决策权限 |
| 失败隔离 | 单调用重试、单规则组隔离、成功单元持久化、失败项可重跑 | 可优化恢复速度，不能因一个失败让长任务结果归零 |
| 严格复用 | 仅复用完整执行指纹一致的成功事实/结果；强制重跑真正绕过 | 可细化缓存层，不能跨代码、模型、提示词、规则或文件复用结论 |
| 提示词单一来源 | 可配置模板、稳定 ID、公共约束共享、结构契约明确 | 可精炼措辞，不能重复堆叠或依赖运行时替换修补 |
| 配置与结果可复现 | 每项任务保留实际生效的规则、模型、提示词和代码/解析指纹；更新全局配置不改写历史结果 | 可压缩快照和优化存储，不能丢失结果产生条件 |
| 可观测执行 | 页面和日志能区分阶段、重试、降级、部分成功、缓存命中及 OCR/图片实际处理范围 | 可优化日志和展示，不能把失败、回退或未覆盖静默伪装成成功 |
| 部署版本可信 | 页面主版本来自镜像内与实际代码同层的构建标记；环境变量和宿主机记录只用于交叉核验 | 可扩展构建信息，但运行代码与部署记录不一致时必须显式告警，部署脚本不得报告成功 |
| 服务商无关 | 模型、腾讯 OCR、多模态差异停留在能力适配层 | 可新增服务商，业务规则不得出现服务商专属分支 |

判断是否“性能或功能不衰减”时，不能只看任务成功和页面能打开；至少同时比较规则召回、关键问题召回、错误高风险、建议分、证据页、失败恢复、总耗时、Token/OCR 调用和峰值资源。任一关键指标下降，默认回退原路径。

## 4. 规则体系与提取契约

### 4.1 规则类别与来源

类别为：资格性、符合性、实质性/废标、其他、客观分、主观分。页面将实质性和废标作为同类业务呈现，但保留历史类别兼容。

来源为：

- `manual`：人工补充；
- `ai`：本轮 AI 提取；
- `ai_edited`：人工修改过检查内容或评分口径的 AI 规则；
- `global`：通用规则库。

展示顺序固定为人工补充/人工编辑、AI 提取、通用规则。页面以勾选启用为主，不提供常规删除入口；旧删除 API 仅为兼容保留。

### 4.2 重新提取

- 重新提取是全新运行：仅人工补充规则作为独立业务口径保留；旧 AI 提取/AI 编辑规则及其勾选、取证设置均删除。旧综合评审/评分/证据结果也删除，不继承、不展示、不复用；旧任务日志可保留用于运行诊断，但不作为业务结果。通用规则库按当前版本重新导入。
- 取证策略是本轮执行设置，不得把规则升级为 `ai_edited`；这样新一轮可按最新原文和证据要求重新规划取证，历史设置也不会制造规则副本。
- 模型附加的条款编号、分段编号或分值尾注不是规则对象。评分去重应先剥离这类机器尾注，再以对象、满分和同源原文合并；无法证明同一事实时保留并在确认前提示，不静默删除。
- “第 X 部分（X 分）”“商务/技术/服务部分（X 分）”等仅表达章节总分的文本是评分守恒台账，不是可执行评分规则；提取阶段应剔除，保留其下具备对象、条件、公式或分档的明细规则。
- 重新提取候选须先做确定性同源去重：非评分规则仅在同类别、同对象且稳定条款 ID 相交或完整原文相同的条件下合并；评分规则另按评分台账、满分和叶子结构收口。语义近似不由本地代码猜测，交给一次规范化和人工确认。
- 编译后的规则以“类别（结论维度）+ 规范化标题（审查对象）”作为最低稳定身份。同类别同名副本即使来自不同原文章节，也必须合并为一条并保留全部互补检查指令、页码、原文、条款 ID 和证据项；本地确定性收口不跨类别猜测。统一规范化只有在确认资格门槛与证明材料属于同一底层事实时才可跨资格/符合类别合并，评分与非评分、材料存在与材料得分始终保持独立。完整规范化格式异常时按类别定向重试，随后仍执行确定性收口，禁止因一次模型 JSON 异常把明显副本直接落库。
- 页面不做空闲常驻轮询；项目可能被其他标签或会话更新时，在窗口重新获得焦点或进入评审规则页时按需刷新当前规则集，避免旧页面数据被误认成当前结果。
- 新草稿内可证明重复的评分副本应立即可逆停用；纯 AI 评分规则无法唯一挂接原文评分条款时，必须阻断确认，不得进入综合评分。
- 新增通用规则立即补入所有未确认项目；修改/删除通用规则不静默改写正在人工确认的项目。已确认项目通过重新提取获得最新通用规则。
- 通用规则全部导入项目，其“是否默认选择”只决定初始启用状态。

### 4.3 提取边界

- 只提取能从投标文件文字、表格、OCR 或图片事实中核验的要求；密封、递交、现场、纸质份数等文件外事实不得形成审查规则。
- 条件性条款必须先确认当前采购包已启用，不得把模板条件句当成实际要求。
- 多包招标必须先识别当前包范围，评分和技术参数不得跨包混入。
- 评分规则必须保留明确满分、计分对象、计分条件、上限和稳定来源条款 ID。每个可执行 `SC-*` 原文评分条款只能归属一个最终可执行评分规则；多个叶子可归入同一规则的 `scoring.items`。父项总分、跨页续行、公式说明只保留为台账上下文，不得成为可执行评分来源。只有本地能证明父项叶子完整覆盖子项时才自动收敛，否则保留全部证据并阻断确认。
- 评分表分部（价格/商务/服务/技术等）必须在原文解析时随叶子条款保存为 `score_sections`，并由最终评分规则继承；分部合计对账优先使用该台账，禁止按 `source_page` 区间猜测归属。来源无法唯一匹配时不自动挂接，确认前必须以 `score_source_unmapped` 明示提示。
- ★技术参数只有同时存在实际标★叶子、实质性后果和证明材料要求时才形成受控规则；同一主题可合并展示，但独立叶子必须保存 `evidence_items`，不能共用一个模糊取证预算。
- 规则合并以同一评审事实为前提；资格门槛与评分、材料存在与材料得分、不同证明材料或不同计分叶子不得因标题相近合并。
- 规则数量由独立评审结论决定，而不是由对象名称、编号、列表层级、分组标题、位置描述或表格行等展示结构决定。同一连续需求只有在产生独立否决、独立评分或独立结论后果时才拆分；否则按当前采购包和连续主题形成少量 `other` 覆盖规则。具体原编号和叶子要求作为内部依据保留，综合评审仍逐项检索，页面默认不展开为大量规则卡片。
- 任何来源派生的补漏候选（包括技术★等）都必须在统一编译之前进入同一去重、覆盖审计和规范化流程；禁止在落库前直接追加特殊规则。确认前校验发现来源、评分或覆盖问题时，只定向修复对应条款，不重新改写完整规则集。

### 4.4 确认规则集

确认前至少满足：

- 有一条启用规则；
- 启用评分规则具有大于 0 的满分；
- 无可确定的重复评分；
- 无同一 `SC-*` 评分条款被多个启用评分规则占用的归属冲突；
- 启用规则满分与招标文件唯一明确总分一致；
- 评分叶子没有明确截断或合计缺口。

OCR/多模态能力不可用属于执行预警，不应与分值结构错误混为同一阻断条件。

## 5. 综合评审与证据契约

### 5.1 全文覆盖

- 长文件从第一页到最后一页按连续页块扫描，不为省 Token 跳页。
- 首轮只建立规则证据和项目范围偏离候选；最终结论按点状、数量累计、章节方案、全文一致性等策略分组生成。
- 每条规则必须获得自身的直接候选页；其他规则的高优先级证据不能挤掉它的唯一证据。
- JSON 异常优先修复短响应或仅拆当前规则目录/规则组，不重复发送整份全文。
- 首轮失败页块必须在最终规则组携带原文或显式标记，不能静默丢页。

### 5.2 项目范围与内部一致性

- 项目范围画像仅来自招标文件和已确认规则；范围候选可以是无关主体、项目、地区、技术内容、设备、标准、服务对象、交付物或其他开放类型，不维护项目特例词表。
- 业绩、资质、人员履历、注册地址、历史合同和合理规范引用不得仅因与当前项目不同而判异常。
- 历史模型的范围候选、风险或结论不得注入新一轮强制重跑。
- 固定响应表单的日期采用本地确定性候选：只读取偏离表、投标函、授权书、声明函、承诺函等落款/签署邻域；标准编号、履历、合同、业绩、证照日期不进入。表单年份不一致或明显偏离招标时点时，必须带入原页并降为人工复核，但不得自动判废。

### 5.3 结果结构

审查状态统一为：满足、不满足、部分满足、未找到证据、需 OCR、需人工判断。每条结果至少保存：

- 规则与规则版本；
- 投标人和文件；
- 关键证据、页码、理由和一句话结论；
- 风险、置信度、证据质量和覆盖状态；
- OCR/多模态状态及分层证据；
- 模型、提示词、代码和输入指纹。

客观分、主观分只展示 `AI 建议得分`，不保存人工调整、有效分或最终分。建议分、计分过程和摘要必须一致；计分过程作为独立证据层，理由不重复规则和 OCR 全文。

扫描型文件或证据覆盖不足时，“未命中”既不等于缺失，也不等于满足。只有实际 OCR/图片证据完整覆盖后，才可恢复确定性结论或建议分；部分覆盖不得外推。

### 5.4 证据分层

当前结果由文字、RapidOCR、腾讯 OCR、多模态和本地确定性事实共同组成。任何后置层：

- 只能补充或纠正其实际覆盖的事实；
- 不得覆盖其他页已成立的全文事实；
- 发生冲突时并列展示并要求人工复核；
- 不得用字符串前缀或展示层正则冒充结构化来源；
- 对客观分只摘要材料、数量、有效性、页码、计分和未决项，不展示整段 OCR 转写。

`EvidencePack` 当前仅承担候选页来源、已核验页和证据层记录，尚未成为全部规则的唯一结论输入；正式迁移见第 10 节。

## 6. OCR 与多模态架构

### 6.1 能力分层

1. **全文机器可读文字**：默认、最低成本。
2. **本地 RapidOCR 基础层**：系统基础能力，但不是每条规则都执行；只在扫描型、文字不足、人工指定或决定性字段需要时处理有限候选页。
3. **腾讯 OCR 增强层**：可选，用于证照、证件、关键字段、低置信或本地识别不完整页；不可用时保留本地结果。
4. **多模态外观层**：可选，只用于签章、勾选、版式、照片、材料外观和其他视觉事实。

本地 OCR 与多模态相互独立；纯文字模型可以完成“全文 + 本地/腾讯 OCR 文字 + 结论”，非多模态模型不得因此阻断任务。

### 6.2 规则级策略

`baseline_ocr_mode`：

- `auto`：文字优先，证据不足或扫描型时有限 OCR；默认值。
- `text_only`：人工明确禁止 OCR。
- `local_ocr`：人工明确要求有限候选页本地 OCR。

增强核验只决定是否追加腾讯 OCR/多模态：不增强、智能增强、每次都增强。智能增强看证据缺口；每次都增强在已定位材料上仍执行一次。强度只控制页数和清晰度，不改变启动语义。

“证书、报告、复印件、扫描件”只是材料名称或载体，不能单独导致每次 OCR。只有签章、勾选、手写、外观等必须看图的事实才强制视觉路径。

### 6.3 资源与兼容

- RapidOCR 懒启动，默认单进程/单执行位；允许短时复用引擎，但空闲后必须退出并释放流、进程和内存。
- OCR 页级缓存绑定文件哈希、页码、渲染和解析器版本；失败、空白、成功分开记录。
- 超大图片在渲染前受像素预算限制。
- 多模态通过能力适配层接入，不得在规则或评分业务代码中写入 MiniMax、腾讯或其他服务商特例。
- 保留历史 `image_mode`、`vision_trigger`、`vision_level`、`vision_status` 等字段兼容；新增状态只能扩展，不能让旧调用方失效。

## 7. 文件查重基线

- 本地负责候选召回和压缩，AI 负责对候选证据提出确认、疑似、排除或证据不足建议。
- 不发送完整文件对；无候选不调用 AI；AI 失败时明确显示未完成并允许重跑。
- 证据必须显示双方投标人名称、各自页码和短原文，不使用无法辨认的 A/B 标签。
- 风险按高到低展示，不保存人工处置状态。
- 招标原文、公共表单和正常主体改写先过滤；表格换行、双栏错位和公共模板不得制造共同删除/共同错误。
- 联系电话、邮箱、姓名、身份证、地址只从明确字段提取；正文长数字不得猜成身份证。
- 系统只生成串标线索，不作法定串标认定，不自动废标。
- 修复误报必须处理对齐、来源分类或候选价值的根因，不得按某句话或某个行业模板加白名单。

## 8. 模型、提示词与全局规则

### 8.1 模型档案

- 模型档案是工作台级配置，不属于项目；可设置默认模型，项目默认选择随之变化。
- 支持禁用、删除和测试连接；禁用模型不出现在项目选择列表。
- API Key 可写入但永不回显。
- 纯文本与多模态能力由人工标记，图片调用前再次校验能力。
- DeepSeek、MiniMax 或未来模型的差异只放在协议/参数适配层，不进入评审规则代码。

### 8.2 提示词体系

右上角提示词配置按三组展示：

- **常用业务指令**：用户经常调整的判断口径和表达偏好；
- **业务流程细节**：规则提取、全文扫描、评审、评分、OCR/图片协作；
- **系统与结构模板**：JSON 契约、字段、恢复和系统边界，通常不应频繁修改。

所有运行提示词必须有唯一来源和稳定模板 ID。相同约束不得在多个模板重复堆叠；公共约束抽成共享片段。能通过业务提示词改善的语义判断优先修改提示词，但以下事项必须修改代码或数据契约：结构校验、分值守恒、缓存身份、页码来源、任务恢复、证据合并和 API 兼容。

修改提示词必须同步：默认模板、可配置展示、模板指纹、定向测试。不得用运行时 `.replace()` 隐式修补用户自定义提示词。

### 8.3 通用规则库

- 通用规则用于跨项目长期适用的评审事实，不用于存放某项目的资格、设备或评分细节。
- 新增规则立即同步所有未确认项目；修改/删除只影响规则库和后续提取，避免改写正在确认的项目。
- “是否默认选择”只决定初始启用状态，所有通用规则仍进入新规则集。
- 通用规则应写清启动前提、检查对象、证据、例外和输出要求；不得依赖模型自行猜适用范围。

## 9. 稳定性、缓存与验收

### 9.1 缓存身份

任何结果复用必须至少绑定：项目/文件哈希、规则集及启用状态、模型档案、提示词模板、解析/OCR版本、核心代码/部署版本和任务输入。`force_rerun=true` 必须绕过整任务、单文件和全文扫描的结果复用。

允许复用确定性事实和完全相同指纹的成功结果；禁止复用其他版本的模型结论、风险、候选优先级或失败兜底。

### 9.2 黄金项目

长期回归项目：

- 山西大学附属中学晋源学校教学设施设备采购项目教学仪器类采购；
- `sxyh`；
- 太原税务 2026 年府西办公区局域网升级改造。

2. 人工规则保留，普通 AI 勾选不继承；
3. 关键问题召回、错误高风险和建议分不劣于基线；
4. 证据页、OCR 页、图片页和最终理由一致；
5. 断连、限流、JSON 截断和单组失败可恢复；
6. 总耗时、模型调用、Token、OCR 页数和峰值资源有记录；
7. 相同输入连续三次不出现无法解释的结果漂移。

## 11. 多 AI 接力规范

### 11.1 接手检查清单

每位开发者或 AI 开始工作前必须：

1. 阅读本文档和根目录 `AGENTS.md`；
2. 执行 `git status --short`，区分用户改动、前一轮未提交改动和本轮范围；
3. 查看最近相关提交和测试，不根据聊天摘要猜当前代码；
4. 明确问题发生层、通用机制和不改变的业务契约；
5. 修改前写出可复现样本或失败测试；修改后做定向和完整回归；
6. 未经用户确认不提交、不推送、不部署。

### 11.2 文档更新规则

以下变化**必须计入本文档**，并优先修改原有章节而不是追加日期日志：

- 产品目标、范围、业务口径、默认行为或人工工作流改变；
- 第 3.4 节受保护核心的行为、责任边界或回退方式改变；
- 主流程阶段增删、数据/API/状态字段改义、兼容策略或迁移方式改变；
- 规则身份、评分守恒、证据来源/覆盖/冲突、缓存复用身份改变；
- OCR、腾讯 OCR、多模态、模型服务商之间的职责、顺序、启动条件或资源上限改变；
- 提示词分组、模板唯一来源、结构化输出契约或用户可配置边界改变；
- 黄金项目、验收指标、未来阶段启动条件达成、取消或被新方案取代；
- 当前存在尚未提交、部署、验证，且下一位必须继续处理的重要工作。

以下内容**不应计入本文档**：

- 不改变任何契约的普通 bug、样式、文案、日志和局部重构；
- 函数名、行号、完整提示词、原始 JSON、长 diff 和测试输出；
- 单个项目、投标人、设备、页码、金额或错误句子的专属分析；
- 一次模型过载、网络中断、临时部署问题和已经恢复的操作过程；
- commit 列表、逐批实施过程、单次耗时或仅用于诊断的临时指标；
- 已完成且长期规则没有变化的提交、推送和部署记录。

具体案例应进入回归测试夹具；实现细节进入代码注释；操作和版本历史由 Git 保存；短期未完工作只进入“当前接力状态”。同一事实只能在本文档出现一次，后续变化必须替换旧表述并删除失效内容，禁止同时保留“旧方案”和“新方案”让接手者自行判断。

规范正文硬上限为 500 行；“当前接力状态”最多 10 条、最多 80 行，全文通常不超过 580 行。超过上限前必须先合并重复章节、删除过时内容，不能通过继续追加突破。每次修改本文档后至少检查标题结构、重复口径、状态标识和 `git diff --check`。

### 11.3 接力记录模板

“当前接力状态”最多保留 10 条，只记录仍影响下一步的重要工作，**不是**按时间机械保留最近 10 条。优先级依次为：未提交但已验证的重要改动、已部署待验收的核心链路、可复现的已知风险、等待用户决定的业务/架构事项、已满足部分条件的计划阶段。相同工作流只保留一条并动态更新，不为每轮尝试新增记录。

- 状态：本地完成 / 已提交 / 已推送 / 已部署 / 待验证；
- 范围：修改了哪个契约或流程；
- 验证：执行了哪些测试和真实项目检查；
- 未完成：明确剩余动作、风险和是否需要用户确认；
- 文件：列出主要文件，不粘贴大段 diff。

工作完成并部署验证后，从接力状态删除；不再影响决策的失败尝试、临时诊断和普通发布记录立即删除；长期有效的决定合并回对应正文，详细过程由 Git 保存。条目接近上限时，先按优先级删除已解决或低影响项，不能挤压正文基线。
