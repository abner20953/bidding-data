# 工作台设计

更新时间：2026-07-27

## 目标与范围

新增独立 Web 模块“工作台”，用于单人、低并发的评标辅助。入口为 `/pingbiao`，API 前缀为 `/api/evaluation-workbench`。

模块包含：

- 评标项目、招标文件/附件与多份投标文件管理；
- 多投标文件查重与横向结果汇总；
- 招标规则提取、人工确认，以及资格性、符合性、实质性和废标点审查；
- 客观分的证据提取与程序计分；
- 主观分的证据化辅助审查；
- 浏览器打印与 CSV 评分报告导出；XLSX、DOCX 留作后续兼容性扩展。

明确不包含：投标文件或技术方案编写、AI 生图、DOC/WPS 转换、本地大模型、多用户协作，以及此前单独列出的上线安全整改。

## 独立边界

- 不修改 `/bijiao`、`/api/compare` 及其响应结构；
- 不影响其他 Blueprint 或 `rokid_glasses_app` 调用的 API；
- 使用独立的 SQLite 数据库 `data/evaluation_workspace.db`；
- 原始文件与解析缓存存储在 `data/evaluation_workspace/<project_id>/`，结构化结果存储在独立 SQLite；打印报告按需生成，不常驻占用磁盘；
- 新功能使用独立 Blueprint、模板、静态资源、服务与任务进程；
- 只在导航页增加“工作台”入口。

## 文件与资源限制

- 第一版支持 PDF 和 DOCX；全文主流程仍以可检索文本为准，未提取到可检索文本的扫描件会明确标记解析失败；对已完成解析、且人工为规则开启图片识别的少量候选 PDF 页，可按需调用腾讯云 OCR 补充图片文字；
- 单文件默认上限 500 MB（可通过运行环境变量 `EVALUATION_WORKBENCH_MAX_UPLOAD_MB` 下调），PDF 解析上限 2000 页，可提取文本上限 200 万字符；
- 每项目默认最多 10 份投标文件；
- 单文件和整批页数、字符数沿用并逐步复用现有 `/bijiao` 的资源边界；
- 文件解析、文件对比和 AI 请求默认并发均为 1；
- 最多保留 3 个排队任务；
- 工作台空闲时不保留工作进程、不加载模型、不建立 AI 连接，也不执行定时扫描。

## 工作流

1. 输入新建项目口令后，创建项目并上传一份主招标文件、招标附件和多份投标文件。
2. 按顺序解析文件并按文件哈希缓存结果。
3. 多投标文件顺序两两比较；本地程序先提取低成本候选证据，再由 AI 对压缩后的候选证据包作结论，形成文件关系矩阵和多文件共同线索。
4. 从招标文件提取资格、符合、实质性、废标、客观分和主观分规则。
5. 用户确认、修改和版本化规则。
6. 对每份投标文件执行“综合评审”：系统按审查、客观分、主观分及小规则组调用 AI，结果仍按审查、客观分、主观分分区展示。
7. 汇总横向结果并导出报告。

## 查重结果

查重沿用现有比对模块对 PDF 的高价值规则：完全雷同、近似雷同、已验证招标共同修改、共同错误、敏感实体、元数据辅助线索及招标原文排除。在此之上增加“横向异常线索”层，分别记录线索维度、S3 人工核验等级、可信度、证据状态、反证提示、判定结果和人工处置，不把多个字段压缩成一个不透明的风险分。

本地程序仅用于生成可比对的候选证据和压缩证据包，不直接给出查重结论。证据包包含投标人名称、各自页码（如“甲公司第 7 页 / 乙公司第 4 页”）、规则名称、最多三条短原文、相似度/次数及反证提示。AI 按批复核这些证据包，输出“确认线索、疑似线索、倾向排除或证据不足”、风险、置信度和建议核验事项；不发送完整投标文件对，不按文件对逐次调用。没有候选证据不调用模型，AI 故障时仅标记 AI 判定未完成。查重复用键包含文件哈希、规则/提示版本和模型公开配置，未变化时自动复用完成结果。

系统仅生成 `collusion_signal`（串标相关线索），不自动生成或认定 `statutory_collusion_condition`（法定串标情形）。多维命中只提高人工复核优先级，不提高法律定性，不触发废标或扣分；工作台不保存“人工处置”状态。

当前实际执行正文雷同、共同异常或错误、共同联系电话、共同邮箱、共同姓名、共同身份证信息、共同地址、招标原文共同改动和相同文档属性九个维度。姓名和地址仅从带明确字段标签的内容中提取，以减少普通文本或模板造成的误报；联系方式、邮箱、姓名、身份证信息和地址在仅限评标使用的横向汇总中完整展示，以便人工核对；元数据只作辅助线索。报价规律、缴费来源、业绩引用、他方主体残留和共同理解偏差因缺少可靠结构化来源而明确披露为“未执行”，禁止从正文数字或模型猜测补齐。后续接入结构化报价时，应使用 Decimal 和中位数/MAD/IQR 等稳健统计，小于 4 个有效样本只做描述性展示。

公共模板处理遵循“先排除、再比较”：提供主招标文件时排除招标原文直接复制，并保留共同实质改动；未提供招标文件时明确降低结果解释力度。其他公共行业模板若未获得确认，不得把模板相似直接升级为串标结论。判定“共同删除”前，系统以两份投标文件全文和该片段在招标原文中的相邻短语为锚点校验：只有被删内容仍在同一条款语境中出现时，才认定为换行或双栏分段造成的提取假象；仅在其他无关条款重复出现时仍保留共同删除线索。义务主体第一人称改写（如“实施方须”改为“我方会”）属于每个投标人的必然响应表述：系统按相邻编辑簇而非单个字符差异识别该表达，相关语气词（“须”→“会”）随主体改写一并保留并打标；全部为这类改动的共同改动信号降权为 C1、不计入配对维度数与复核优先级；只要混入任何其他实质改动，信号维持 C2 且优先级逻辑不变。

结果包含：

- 文件关系矩阵：每个文件对的独立线索维度、线索数量和人工复核优先级；
- 正文雷同、目录、元数据、图片、共同错误、共同修改；
- 文件标签、页码、原文对照和风险说明。

图片第一版只做原始图片哈希与位置记录，不做 AI 图像语义识别。

## 审查与评分

招标规则须先由 AI 提取并经用户确认。规则提取提示词要求模型基于完整语境排除仅能在递交、密封、开标现场或纸质份数环节核验的要求；后端不再以关键词硬过滤，避免把“投标截止日前若干年”等业绩有效期误删。每条规则同时保留“检查规则”（面向 AI 和页面的明确核验指令）与“招标原文依据”（可追溯的原文摘录）、名称、类型、页码、是否需要 OCR、评分方式和启用状态；所有保留的检查点均交由 AI 判断。页面以检查规则为主，原文依据用于核验与报告追溯；规则修改后形成新版本，旧结果保留并标记其使用的规则版本。人工补充规则可增加资格性、符合性、实质性/废标项、客观分、主观分和其他规则；补充客观分或主观分时必须明确满分，客观分还可选择“满足即满分”或“按评分规则由 AI 建议得分”。当前规则集不展示具体评分参数，保持规则浏览界面简洁。

规则提取会先在本地定位“得 X 分、最高 X 分、满分 X 分、分值、扣 X 分”等疑似评分条款，为每个明确计分行建立独立且稳定的 `score_clause_id`，并把短片段作为 AI 的评分覆盖清单。相邻的业绩、人员、报价等评分行不得合并成一个覆盖包；覆盖优先依据条款 ID，其次才使用原文与计分数字的严格交集，不再按规则名称中的任意短词判断。仅把仍未覆盖的条款和截至当前批次的既有评分规则发送给 AI 补提取。本地不会直接生成评分规则或分数。这一机制适用于业绩、报价、人员、资质、方案及其他明确计分项。

技术参数中的“★”采用受控的实质性规则识别：只有招标原文同时存在实际标★技术叶子项、明确“★为实质性/必备指标”及不满足的无效/拒绝后果、并要求投标文件提供技术资料、参数、截图、检测报告、证书、说明书等证明材料时，才保留一条按连续参数表或设备主题归并的“★技术参数及证明材料响应”规则。该规则独立于 #/△ 评分规则和普通技术覆盖规则，核验全部★项的逐项响应及与所投型号对应的证明材料；证明材料可能兼具文字和图像时默认采用文字审查加可选图片复核，不会强制整条进入 OCR 状态。提示词在映射、编译、覆盖审计和质量门控各阶段均执行该口径；另有同样严格的本地兜底，只在模型遗漏且三项条件均成立时补入一条规则。多包文件若无法由本地可靠归属技术★条款到当前包，则不使用该兜底，仍交由带分包上下文的 AI 提取，避免跨包污染。

当前规则集在待确认状态下默认启用无需 OCR 的规则；需要 OCR 的规则默认不勾选，用户确认具备相应核验条件后可逐条启用。未启用的规则会保留在该版本中以便追溯，但不参与确认后的综合评审或评分。页面不提供删除规则入口，以启用状态作为规则取舍的唯一操作；至少保留一条启用规则后方可确认规则集。为兼容既有调用，后端删除接口暂时保留但不在页面暴露。

资格、符合、实质性和废标审查结果统一使用：满足、不满足、部分满足、未找到证据、需 OCR 后判定、需人工判断。页面以中文展示 AI 结论，并按投标人分组，在每位投标人内按照异常优先、高中低风险排序；分组可以展开或收起。每条结果包含招标依据、投标证据、页码、理由、风险级别、置信度和证据完整度。OCR 只能降级其自身决定性事实：一条可由文字审查、同时附带少量证照或截图待 OCR 的综合覆盖规则，若已经发现文字层缺项、矛盾或部分覆盖，必须保留原有部分满足/风险结论，并在证据中另列待 OCR 子项；不能把整条规则错误改成低风险“需 OCR 后判定”。

工作台采用 AI 优先，页面仅展示 AI 建议，不提供一键确认、人工调整、有效分或最终分写回。评分页面、打印报告和 CSV 都明确展示“AI 建议得分”。需要图片文字或盖章识别的规则会被明确标为“需 OCR 后判定/评分”；图片识别关闭、未定位页面或 OCR/模型不可用时，不得据此把投标文件判为不满足。

### 扫描件证据覆盖保护（已实施）

系统以文件机器可读文本密度作为通用保护信号：页数不少于 3 页且平均每页不足 80 个可读字符时，视为扫描型或文本覆盖明显不足。此时“文本未命中”既不等于材料缺失，也不等于规则满足。综合评审提示词会收到覆盖不足边界，后端再独立执行同一保护，防止模型输出被绕过：未获得实际 OCR 或图片识别**完整覆盖**的审查规则统一回落为“需 OCR 后判定、低风险、证据缺失”；客观分和主观分清空暂定建议分，页面显示“待 OCR 后评分”，不会把未定位的扫描材料显示为 0 分。只有 OCR 或多模态结果按证据协议确认已完整覆盖该规则后，才允许恢复满足/不满足结论或建议得分；部分覆盖只保留已确认事实，不得外推为整条规则结论。结果持久化 `coverage_status=covered|partial|uncovered`，供页面、报告、重跑与审计统一使用。扫描型文件不复用旧的纯文本综合评审结果，确保新的取证策略真正执行。

客观分与主观分均由 AI 根据明确的招标依据给出建议分、证据页码和理由；不保存人工调整、有效分或最终分。数量、阈值、分档、累计上限和价格公式仍只以受限规则结构扩展，禁止执行模型返回的表达式。

AI 提取客观分和主观分时必须返回 `scoring.max_score`。若模型遗漏，但招标原文明确包含“总计/最高/最多/满分 X 分”等表述，工作台仅从该原文补齐满分，并标记为“从招标依据识别”；对于数量累计、区间、分档等客观分，默认保持人工评分，不会误作“满足即满分”。待确认规则中的评分满分可直接在规则表内修改保存，无需删除规则重建。

主观分先按同一规则版本、模型档案和 Prompt 版本独立审查每份投标文件，再做横向汇总。客观分与主观分结果均按投标人分组展示。输出 AI 建议得分、证据页码、优点、不足、得扣分理由和置信度。

## 模型档案

模型档案是工作台级全局配置，通过页面右上角“模型配置”入口维护，不归属于任何单一评标项目。项目内各任务只选择已配置的模型档案。

模型档案保存显示名、协议、Base URL、模型名、上下文长度、超时、JSON 模式和思考模式。API Key 可以手动录入：系统用工作台独立密钥加密后保存，密钥文件位于被忽略的 `data/` 持久化目录；读取、编辑、模型列表和 API 响应均不返回明文或密文，只显示“已配置”。旧的 API Key 环境变量配置继续兼容。

每个模型档案提供“测试连接”，以极小请求验证 Base URL、模型 ID、API Key 和兼容参数。测试不写入评标项目数据，也不记录 API Key。

## 腾讯云 OCR 与多模态补充

页面右上角“模型配置”内分别提供“OCR 文字取证”和“多模态图片外观识别”两个独立总开关。OCR 开启后可选择“优先腾讯云、不可用时回退本地 RapidOCR”或“仅使用本地 RapidOCR”；多模态开启后，才会向人工标记为多模态的图片模型发送图片。关闭其中一项不会连带关闭另一项。腾讯 OCR 的 SecretId、SecretKey 使用工作台独立密钥加密保存，读取和 API 响应均不返回明文或密文。

### 本地 RapidOCR 回退（第一阶段，已实施）

为避免腾讯云 OCR 免费额度耗尽后完全失去文字识别能力，系统增加本地 `RapidOCR / PP-OCRv5 mobile / ONNX CPU` 路径。全局 OCR 总开关控制是否执行文字取证，独立的路线选项决定“腾讯优先、本地回退”或“仅本地”。腾讯 OCR 正常返回文字、页面已确认空白或图片本身不适合 OCR 时，不额外调用本地 OCR。腾讯密钥、地域、接口和额度仍在独立的“腾讯云 OCR 配置”区域维护，切换路线不会清除这些配置。

本地 OCR 采用一次一批的短生命周期子进程，主 Web 服务和常规评审 worker 均不导入 ONNX Runtime；子进程仅处理当前规则已筛出的临时 JPEG，完成、超时或异常后立即退出，临时图片自动删除。因此未执行本地 OCR 时模型不驻留内存，也不改变非 OCR 流程的 CPU、内存和时延。子进程限制数值库线程为 1，检测长边默认 960（可通过 `RAPIDOCR_LIMIT_SIDE_LEN` 在 640-1280 间调整），PDF 页仍受现有识图强度页数上限约束；本地识别结果使用独立缓存键、独立“本地 RapidOCR”证据层，并只能补充可见文字，不能据未识别内容判定缺失、不得分或不满足。证书外观、签章、勾选、真实性、复杂表格结构仍由腾讯专项 OCR、多模态模型或人工复核承担。

本地 OCR 在 2 核 2 GB 环境中必须全局单路执行：多份投标文件的远端模型请求仍可按既有策略并行，但 RapidOCR 子进程一律排队启动，避免多个 ONNX Runtime 同时抢占内存。全系统“图片识别 / OCR”开关开启后，本地 OCR 的可用性只取决于本地运行环境，不依赖多模态模型档案；即使图片模型被禁用，纯文字 OCR 规则仍可执行，明确需要图片外观事实的规则会保留文字/OCR建议并标记图片未完成。历史 `check_mode=ocr` 规则一律按“文字 OCR＋图片核验”的混合链路兼容，不能因旧元数据只标记视觉而跳过本地 OCR。候选页按规则强度与材料角色决定本地渲染质量，证照、表格和精细核验使用较高清晰度，普通正文保持快速档；所有 OCR 渲染均在生成 Pixmap 前按像素预算压缩，避免超大图纸触发瞬时内存峰值。子进程逐页返回“已识别、空白、失败”状态：空白页写入独立缓存，失败页会使 OCR 归纳只能形成部分结论并在结果中说明，不能被其他成功页掩盖。

第一阶段的验证范围包括：本地 OCR 子进程超时/缺包/异常时自动保留原结论；腾讯 OCR 正常成功时不启动本地 OCR；额度或配置不可用时本地结果可进入原有 OCR 归纳、证据层、评分摘要和图片复核流程；页级缓存命中不重复启动子进程；空白页缓存、单页失败保守降级、并发投标文件下本地 OCR 单路闸门和本地用量统计均通过回归；任务完成后系统无 `rapidocr` 子进程。当前代码还会为每次真实本地 OCR 子进程记录处理页数、识别/空白/失败页数、耗时和峰值 RSS，不保存图片或识别文字；页面显示本项目的平均秒/页和最高内存。历史缓存页没有这类运行指标，不能反推或混入验收样本。部署后仍应使用至少 30 页实际投标扫描页进行云端验收，并人工记录文字召回率、Swap 和综合评审总耗时。

### 本地 RapidOCR 优先（第二阶段，暂不启用）

只有同时满足下列条件，系统才可以主动提示用户评估第二阶段；在此之前，界面和默认流程必须保持第一阶段的“腾讯优先、本地回退”策略：

1. 云端验收至少覆盖 30 页实际扫描件，关键文字（证书名称/编号/有效期、金额、日期、声明函字段、表格行列）人工核验召回不低于腾讯当前基线，且未出现把未识别文字解释为材料缺失的错误；
2. 连续 3 次完整项目任务中，本地 OCR 子进程峰值 RSS 不导致容器进入持续 Swap，单页与整项评审耗时不劣于腾讯 OCR 路径的可接受基线，失败、超时和缺包均能自动回退；
3. 缓存命中、重新评审、图片识别联动、客观分摘要、报告/CSV 和多项目全局 FIFO 队列均通过回归；
4. 完成 PP-OCRv4 mobile 与 PP-OCRv5 mobile 的同页 A/B，基于实际招投标扫描件选择唯一生产模型；不得仅根据公开基准切换。

条件成熟时，工作台应在 OCR 配置页显示“可评估第二阶段”的非阻塞提示，并附最近验收指标；启用第二阶段仍必须由用户在配置页明确确认。第二阶段仅允许普通扫描正文、承诺函和非结构化应答表先走本地 OCR；证书/证件精确字段、营业执照、复杂表格、签章和视觉事实继续遵循当前腾讯 OCR/多模态优先链路。任何准确性、稳定性或总耗时回归，立即切回第一阶段。

每页图片只在内存中渲染一次，以文件、页码、图片哈希和 OCR 接口为键缓存结果。系统不再固定使用单一接口，而是按规则内容、识图强度、接口是否启用和当月剩余额度生成质量有序的候选链：营业执照、表格、高精度、通用印刷体等专用场景优先使用匹配接口，普通低清晰度任务可优先使用精简版或高速版，调用失败或额度不足时自动顺延到下一项。高速版和精简版属于腾讯云老接口，新账号不一定具备权限，默认关闭；账号确认具有对应免费包后可在模型配置中启用。各接口分别维护自然月调用台账和可配置的安全上限（默认 900 次，预留额度给人工排障）。所有真实外发请求无论成功或异常均保守计为一次；鉴权、接口不支持和额度不足属于服务级故障，会在当前规则内停止使用该接口；临时过载/网络异常只对当前页受控重试一次，单页图片参数异常只切换该页，不会误禁用后续候选页。腾讯 OCR 不可用时先由本地 RapidOCR 接管文字提取；规则还需要签章、勾选或外观事实且多模态已启用时，再补充图片判断。两类能力均不可用时保留原有文字结论并明确展示未完成原因，不终止综合评审。

腾讯专用接口的结构不能统一拍平成无标签文字：营业执照保留“统一社会信用代码、企业名称、法定代表人、住所、期限”等字段名，表格识别保留表号及单元格行列，普通文字接口保留原始文字行。解析器版本进入页级缓存；结构升级后旧缓存不复用，避免历史错误字段继续参与结论。单条规则命中多页时，OCR 提示上下文按页公平分配字符预算；长页优先保留与规则标题、检查规则和评分子项匹配的行及其邻行，再均匀保留首尾与必要上下文，不能让前两页或页首文字挤掉中段关键表格行。

系统按规则提取阶段保存的 `evidence_requirements` 优先区分“文字 OCR”“纯视觉”“混合”三种策略，旧规则缺少结构元数据时才回退到通用关键词判断；避免 OCR 的文字结果被误当成图片事实。普通文字、表格和声明类混合规则沿用“腾讯 OCR → 文本模型结构化复核 → 多模态补充视觉事实”的稳定链路；证书、证件、营业执照、人员资格证和平台查询截图等材料本体规则，在启用多模态且确需图片判断时采用“多模态找准材料页并直接逐字提取相关字段 → 仅对已形成图片证据的页调用腾讯 OCR 独立复核”的视觉优先链路。后者不会再对目录、承诺函等普通候选页预先消耗 OCR 额度，也不会为 OCR 再发一次文本模型请求；图片结论保持主结论，OCR 原文保留于页级缓存和证据层，页面仅显示简短复核摘要。多模态未定位、调用失败或未覆盖时必须回退到原 OCR 链路，不能因优化降低材料覆盖率。混合策略的规则若规则文本未明确签章、外观、截图样式等纯视觉核验目标，且人工触发方式为文字不足时补充（text_fallback），腾讯 OCR 完整覆盖后不再调用多模态模型，并在结果中明示跳过原因；人工显式要求（required）的规则始终执行图片识别。纯视觉规则即使用户选择快速档，单页渲染清晰度也不低于 scale 1.8；内部使用 `standard` 质量档位，再由网关按服务商映射为合法图片参数，页数预算仍由人工档位决定。OCR 只能补足可见文字，不能证明签章、原件、真实性或线下条件；这些结论必须由多模态图片和人工复核共同完成。OCR 复核和多模态图片提示词分为可维护的业务指令与“系统与结果结构”中的输出/证据协议两层；两层均可在右上角查看、编辑和恢复默认，但保存时会校验必要输出字段，避免误删页码、覆盖范围或冲突协议。它们均进入任务指纹，避免复用旧结果。

人工选择的识图强度表示清晰度与覆盖预算，不表示机械截取前一、二或三页。系统优先采用全文扫描台账中保存的实际 PDF 页号，目录页码和页面自印页码只作后备；候选页定位完全使用本地数据，不增加任何外部调用：解析文本页眉/页脚中独立成行的印刷页码用于估计“印刷页码→PDF 页序”的固定偏移（样本不足 8 页或一致比例不足 60% 时不纠偏），目录语境引用的页码按该偏移换算为 PDF 页序；文字证据页相邻的纯扫描/图片页（解析文本极少）作为附件本体候选紧随其后。快速、标准、精细档首轮分别最多发送 2、4、6 个候选页。标准和精细档在首轮结论不完整（partial/none）或模型主动报告未覆盖时主动覆盖下一批；首轮已完整覆盖且无冲突时提前结束，不再为剩余候选页消耗多模态额度；模型报告未覆盖时还会跨不同证据分支补充相邻页。若全文索引命中同一密集、等间隔附件序列的多页但漏掉中间纯扫描页，系统会在有限页预算内自动补齐该序列，不会把稀疏目录范围展开成大量图片调用。这样既避免单次多图请求过重，又可在不逐页识别整份文件的前提下完整覆盖并列证书、多名人员证件和连续附件。

OCR 与图片结果按证据层协同：全文扫描可确认非视觉子项的存在或未发现，候选页图片解决证书、截图、签章等剩余视觉子项；两层合并后覆盖整条评分规则时，允许重新给出整条规则的建议分，避免理由已经算出新分而页面仍保留文字层旧分。结果同时保存“检查页”（实际发送或已调用页）与“证据页”（模型明确用于结论的页），页面、CSV 和报告不得将两者混为一谈。客观分主表仅展示 OCR 的材料类别、数量、有效性、页码、计分结论和未决项；原始 OCR 明细仅在可展开的证据链中保留，结构化归纳失败时不附整页 OCR 原文。

OCR 调用页与 OCR 实际证据页分开记录：前者仅表示已消耗额度处理过的页面，后者必须由 OCR 归纳结果明确指出且限定在本次调用页内；多模态同样只将本批实际形成证据的页写入证据页，不能把全部送图页当作证据。多模态优先复核 OCR 实际证据页，并继续保留全文扫描、计分明细等原始候选，避免 OCR 找对页后图片模型又重新送错页。多批图片识别时，后批请求必须携带前批已识别事实；模型按“全文文字 + OCR + 全部图片批次”形成单一最终结论和建议分。证据合并采用新补充保留策略，即使原文字理由已接近字段上限，最新 OCR/图片结论也不会在尾部被截掉。影响结论或计分的实质冲突必须同时给出清晰的文字值和图片值；没有逐字对照证据的模型自报冲突只作为一般疑点，不冻结建议分。

精细模式遇到完全没有可检索页码的纯扫描文件时，只执行一次低清联系表找页；找页结果先交给腾讯 OCR 提取文字，再复用给高清多模态核验。腾讯 OCR 失败或额度不足时仍保留这批候选页，图片阶段不得重复找页。

worker 仍按任务临时启动、空闲时退出，不增加常驻进程。标准输出与异常堆栈写入数据目录下的 `worker.log`，达到约 2 MB 后轮换为单份 `worker.log.1` 备份，便于排查外部模型返回异常，同时限制磁盘占用。

### 候选页路由与跨层结论一致性（2026-07 第一轮）

图片识别的首要风险不是 OCR 或多模态模型本身，而是把目录、技术应答、承诺函或无关附件错当成证明材料。因此，候选页按以下通用优先级排序：目录中“材料名称……页码”的显式条目（经印刷页码到 PDF 页序的偏移换算）、规则所需材料本体页、OCR 实际证据页、全文扫描页码、模型普通页码和相邻扫描页。目录只负责定位，不能作为材料已提供的证据；目录识别以页首“目录”标题或至少三条引导符条目为准，避免把正文的“产品目录”等字样误判为目录。目录续页按连续引导符链式读取，单个目录首页最多延伸 8 页；这既覆盖长目录中后部的证书、合同和声明函条目，也不会把正文零散点线无限扩张。目录显式命中同时进入 OCR 与图片候选链，优先于目录页、承诺页和技术应答页。规则与目录条目通过长材料名片段匹配，不采用地区、设备、项目名称等专属补丁。候选页面还会区分目录、响应函、授权委托书、营业执照、证书、查询截图、合同、验收证明、身份证/人员证件、招标要求和纯扫描页等材料角色；合同签章页不得替代响应函签章页，要求复述页不得替代证书本体。无法从本地文本判别的纯扫描页仍保留，避免因过滤造成漏证。

腾讯 OCR 的接口选择同时考虑规则和候选页角色。营业执照专项接口仅在当前页的本地文本包含“营业执照”或“统一社会信用代码”特征时调用；错误候选页改走通用链，但不影响同规则后续真正的营业执照页继续尝试专项。证书、身份证、人员资格证和平台查询截图优先采用高精度识别；普通清晰正文可采用高速或精简接口；签章、勾选和外观事实由多模态图片负责。OCR 后、送多模态前会将直接材料页和 OCR 实际证据页排在前面，无关页只作为最后兜底；多模态模型明确标记为无关的页面只能保留在“检查页”，不能写入“证据页”。

最终展示必须消除陈旧结论：后续 OCR/图片已清晰确认某项证书、合同、执照或截图存在时，旧结论中同一材料的“未见、未提供、待 OCR 核验”等短句应自动移除；未覆盖的其他材料仍完整保留。客观分的图片补充在 `partial` 状态下默认仍保持原分数，但若模型返回与评分规则叶子项 ID 对应、且每项均有实际证据页的 `score_items`，系统允许只上调已完整证实的叶子项并按其分值上限和总分上限确定性求和。没有结构化叶子项或证据页时绝不改分，防止零散图片说明造成误计分。结果理由、证据和建议分保存前必须保持一致。

MiniMax 的综合评审请求保留模型档案配置，但在 `evaluate_all` 阶段将单次读取等待限制在最多 240 秒；超时后复用既有“仅重试当前规则组、保存已完成结果、必要时拆分规则组”的恢复链，避免单次 600 秒卡死拖垮整项任务。

### EvidencePack 候选页复用与后续演进边界

为提高 OCR/图片识别链路的可追溯性，系统在综合评审完成后额外保存按“任务、投标文件、规则、评审组件”隔离的 EvidencePack。当前版本为 `candidate-v2`，记录既有流程已经产生的全文扫描线索、基于规则结构生成的材料观察清单、OCR/图片证据摘要、检查页、证据页和候选页来源（全文扫描、本地召回、运行时候选、OCR 命中或图片实际检查）。同一**文件 SHA256**、同一保守材料键（材料角色、证据维度和材料锚点均一致）重跑时，只会把历史 OCR/图片**直接证据页**加入本轮候选页的最前列；目录、全文扫描和文本锚点等原候选来源一律保留。它不复用旧状态、建议分、理由、风险等级或模型结论，也不改变对外 API，因此不能因旧结果错误而污染新一轮判断。该表随项目、任务、文件或规则删除自动级联清理，单条记录不保存 OCR 全文且限制大小，适配 2 核 2 GB 服务器。

规则可用 `evidence_requirements` 标记取证维度：`text`（文字/表格）、`document`（材料本体）、`field`（编号、日期、金额、型号等关键字段）、`visual`（签章、勾选、扫描图片或外观）、`cross_bid`（横向比较）和 `external`（外部核验）。这些字段只形成同一结论规则的取证计划，不能拆成重复审查点；为兼容历史规则，`document` 或 `field` 会自动同时保留 `text` 路由。

### 图片取证三轮稳态改造（2026-08，已完成）

本轮目标是让“材料本体＋关键字段”的一般性规则更容易获得恰当的图片证据，同时不改变历史规则和纯外观规则的运行语义；不以具体设备、证书或行业名称作为判断条件。

1. **交互与兼容层**：项目规则以“智能取证、扫描文字核验、签章/外观核验、文字与外观双重核验、不开启”表达策略，并独立显示快速/标准/充分的覆盖上限和执行预览；原有 `image_mode`、`vision_trigger`、`vision_level` 继续保存、继续由 API 返回。确认规则集前只读预检能力/预算矛盾，只提示不拦截。新建通用规则默认不增加图片调用，避免无意扩大服务器负载。
2. **计划器影子层**：每条综合评审结果的 EvidencePack 记录通用取证计划（材料观察清单、关键字段、候选页、OCR/图片预算、实际执行页和停止条件），`decision_participation=false`。它不改变候选页、调用、分数、状态或对外 API，可用于后续审计和 A/B 对照。
3. **受控接管层**：仅当用户在规则上**明确保存**“智能/扫描文字/双重核验”策略，且取证维度包含 `document` 或 `field` 时，才采用 OCR 优先；OCR 未覆盖、失败或未识别到至少两类可验证字段时，继续原候选页并按原有条件回退多模态。签章、勾选、外观等纯视觉事实仍保持视觉优先。历史规则（包括升级时读取后推导出的策略）不因本轮升级改变顺序。

后续可考虑的增强仍必须先做影子 A/B：以 EvidencePack 比较“计划候选页/实际证据页”的命中率、漏检率、客观分差异、人工关键问题召回、任务失败率、耗时、OCR 页数和图片 Token。只有准确性、稳定性和可恢复性均不低于基线时，才可让计划器调整候选页排序或尝试一次最终归纳；不得删除旧候选来源或仅凭缓存页作结论。

### 图片取证交互基线（2026-08，已实施）

规则确认页和通用规则库的日常设置统一为两项：**图片取证**（不启用、智能取证、每次都取证）和**取证强度**（快速、标准、充分）。不启用时不展示强度，也不会形成“策略已启用但强度关闭”的矛盾组合。智能取证适用于绝大多数规则，仅在文字证据不足、扫描件/图片为关键证据时按需处理候选页；每次都取证表示“每次评审均检查候选材料”，适用于签章、勾选、照片、版式、图纸、截图等不宜遗漏的事项，但仍由系统根据证据类型决定应使用 OCR、图片模型或两者协同。快速用于单页材料或快速抽查，标准用于通常材料，充分用于材料分散、页数较多或风险较高的事项。

OCR、图片模型和启动条件属于**专家模式**，默认折叠。日常用户无需组合“仅 OCR / 仅多模态 / 双通道”或底层启动字段；系统在规则旁说明适用场景、预计路径和当前能力状态。专家模式仅用于明确限定通道或保留历史自定义配置，修改后显示“专家自定义”，可一键恢复系统建议。前台简化语义继续映射到既有 `image_mode`、`vision_trigger`、`vision_level`，并新增 `always` 预设（`auto + required`）；历史 API 字段、任务执行链路和外部调用不变。

后续若考虑让 EvidencePack 参与决策，必须按照下列顺序灰度验证，任何一项未达到要求都不得改变现有流程：

1. **影子观察期**：至少覆盖多个不同格式、扫描比例和评分复杂度的真实项目。比较新记录中的候选来源与当前实际处理页，确认记录完整、来源解释正确，且不会引入磁盘或任务耗时异常；
2. **计划器影子期**：新的取证计划器只能计算“建议 OCR 页/图片页/预算”，不得实际调用或排除旧候选。必须证明其不会遗漏当前流程命中的关键页、评分叶子项或人工已确认问题；
3. **排序灰度期（已实施，候选页限定版）**：仅允许历史已验证命中页作为候选排序加分，实际候选集保持“旧流程候选页 ∪ 历史命中页”，不得仅使用缓存页。当前以文件 SHA256 与材料键隔离，且只复用 OCR/图片已直接证实页；后续若扩大复用范围，仍须把 OCR 解析器版本、图片模型、渲染参数和提示词证据协议纳入失效条件；
4. **最终归纳试点**：仅对 `required` 或文字＋视觉混合且材料清单已完整覆盖的规则试点。现有文字/OCR/图片结果必须先逐步落库；新的最终归纳失败、超时或格式异常时，必须立刻回退到当前合并链，不得重新发送全文、OCR 或图片；
5. **推广门槛**：除新旧结果一致率外，还必须验证人工关键问题召回、证据页准确性、客观分差异、错误高风险数量、模型异常恢复率、任务失败率、总耗时和 Token/图片调用量。准确性、稳定性和可恢复性任何一项下降时不得推广。

不在当前阶段实施的事项包括：用 EvidencePack 替换现有候选页逻辑、缩减状态类型、删除字符串合并兼容层、把多阶段取证强制改成一次模型结论，或为了节省 Token 减少全文证据覆盖范围。

### 两阶段 OCR（2026-08，已实施）

OCR 候选页先做小范围“发现”识别：普通单一材料/字段规则在低、中、高强度下先处理 2、3、4 页；只有本地文字明确命中规则的材料词或材料角色时，才停止继续处理无关尾页。未命中、OCR 失败、扫描件文字过少时必定继续处理剩余原候选页，绝不能把“首轮没识别到”当作材料缺失。按数量累计的客观分、含叶子评分项的规则、分段/一致性规则和固定表单规则始终覆盖完整原候选页预算，防止少看一页导致漏证或少计分。OCR 归纳模型仍只在全部已处理页汇总后调用一次，旧的错误恢复、腾讯云优先与 RapidOCR 回退链路不变。

### 模型无关的多模态兼容原则（2026-07）

图片识别能力不得绑定 MiniMax M3、某个模型名称或某一家服务商。MiniMax 只是当前已验证模型之一，不是业务架构的默认协议。规则路由、候选页定位、OCR 协作、证据合并、评分和结果展示只能依赖统一的内部能力描述与证据协议；服务商差异必须收敛在 AI 网关适配层，禁止继续把新的模型名称、Base URL 或私有参数判断散落到评审业务流程中。

内部图片请求应先形成与服务商无关的 `VisionRequest`：包含带稳定 PDF 页号的图片资产、MIME 类型、像素尺寸、质量档位、规则包、已有文字结论和预期结果协议。网关再根据模型档案中的协议适配器转换为 OpenAI Chat Completions `image_url`、OpenAI Responses `input_image`、Anthropic Messages `source.base64`，或未来其他兼容格式。业务层不得直接构造 `image_url`、`detail` 或特定响应包路径。内部质量档位只使用 `low / standard / high`；适配器负责将 `standard` 映射为服务商支持的 `auto`、省略参数或其他合法值，不能把非标准值原样发送。

模型档案的“支持多模态”不能只依赖人工勾选。保存后仍由人工决定是否启用，但“测试连接”应分别验证文本结构化输出和一张极小测试图片，记录以下可公开能力：请求协议、是否接受 Data URL 或原始 Base64、单次图片数、单图与总请求大小、支持的 MIME 类型、是否支持清晰度参数、图片模式下的结构化输出方式、输出上限字段、思考参数、响应正文位置、可重试错误和建议并发。探测失败只停用该档案的图片能力，不影响其文本能力；探测结果不得包含 API Key、响应正文或测试图片内容。

所有多模态服务商最终都必须归一为同一份内部 `VisionResult`：覆盖范围、结论范围、证据页、无关页、关键字段、评分叶子项、冲突级别、补页请求和简短证据。页码、枚举、分数上限和证据页必须由本地代码再次校验；模型未返回证据页时，多页请求不得直接形成完整结论或改分，单页请求才可在明确覆盖时安全回填该页。模型输出字段名称或响应外壳的差异只能由适配器处理，不能改变业务结果字段和既有 API。

为适配腾讯云 2 核 2 GB 服务器，图片渲染必须在生成 Pixmap 前按页面尺寸和最大像素预算计算缩放比例，避免超大图纸先占满内存后再压缩；单页降采样不得污染同批后续页面的清晰度。渲染资产按“文件哈希、PDF 页号、缩放、质量、MIME”在任务内复用，任务结束释放，不新增常驻进程。图片并发由能力描述和运行时健康状态控制：默认两路（`VISION_PARALLEL_LIMIT` 可在 1-4 间调整），单份投标文件内部仍按规则顺序执行，只有多家投标文件同时进入图片识别阶段时才真正并行；遇到 429、529、超时、413 或服务商过载立即回退并只重试当前最小单元。

跨模型兼容改造必须采用适配器增量接入：既有 OpenAI-compatible 路径保留为第一个适配器，外部 API、规则字段和结果字段不变。每接入一种新协议，至少用相同 PDF 页、相同规则和相同图片预算做 A/B 回归，比较关键问题召回、证据页准确性、建议分、错误高风险、格式恢复率、耗时和图片 Token；准确度、稳定性或可恢复性低于当前基线时不得设为默认图片模型。

### OCR 与多模态后续优化门槛

后续高收益改造按稳定性分三层推进；其中第一层已于本轮实施，后两层仍须按灰度门槛验证：

1. **低风险基础层（已实施）**：修复逐页渲染参数串扰；增加渲染前像素预算；显式页 OCR 仍受人工强度页数上限约束；视觉结果缺少合法证据页时不允许多页请求直接改分；成功但无文字的 OCR 页做缓存；图片模型连接测试增加真实小图探测；同一任务内复用已渲染的 JPEG 页面。这些改动不改变候选来源和业务规则。
2. **兼容与复用层（候选页复用已实施，协议适配仍待灰度）**：EvidencePack 已按同文件哈希与保守材料键把历史直接证据页作为候选排序加分，候选集合继续保持旧来源并集；服务商无关的 `VisionRequest / VisionResult` 与非 OpenAI-compatible 协议适配仍需按同页 A/B 逐个接入，不能把文档中的目标结构误认为已支持全部服务商协议。
3. **证据融合验证层（影子记录已实施）**：视觉优先后的腾讯 OCR 不能只显示“已复核”。图片模型返回的关键字段与 OCR 原文已在 EvidencePack 中形成结构化影子核对：完全一致才标记独立命中，未命中只表示无法交叉验证，绝不形成冲突或改分。只有同一字段两侧均清晰且值不同，且经过后续 A/B 验证后，才允许它消除陈旧“待 OCR”结论或提高置信度。

暂不直接上线“同页一次通用识图供所有规则复用”或“把多条规则合并为一次图片结论”。这两项虽然可能大幅减少图片 Token，但通用识图容易漏掉规则特定细节，多规则单包也更容易出现字段串扰和格式异常。只有页级结构化视觉事实的真实召回率达到现有逐规则识图基线，并保留按规则补看图片的兜底路径后，才可灰度试点。

## 提示词配置

页面右上角提供与模型配置同级的“提示词配置”入口，进入和查看无需口令；只有保存修改或恢复默认时才逐次校验 `108`。可查看、修改或恢复默认的模型连接测试、文件查重 AI 复核、评审规则提取与评分补充、单项审查、客观分、主观分、综合评审全文覆盖扫描和最终规则组复核的系统提示词及任务提示词；修改作用于后续新任务，且会进入任务复用指纹，避免错误复用旧结果。规则、文件正文、证据包及 JSON 输出所需的运行时数据以 `{{变量名}}` 占位符注入；保存时会校验必需变量未被删除，因此用户可以编辑全部指令文本而不会丢失运行时数据。

## 全局通用规则库

页面右上角提供与模型配置、提示词配置同级的“通用规则库”，可直接查看，无需口令；新增、修改或删除每次都必须输入 `108`，服务端逐次校验。规则库仅支持资格性、符合性、实质性/废标项和其他规则，每项包括名称、明确的检查规则、可选招标原文依据及 OCR 标识。**全部**通用规则会在新项目创建以及每次重新提取待确认规则时复制到项目；“是否默认选择”只决定复制后项目内复选框的初始状态，不决定是否导入。新增一条通用规则后，系统还会立即补入所有当前最新规则集仍为“待确认”的项目；没有规则集的早期项目会创建只含该规则的待确认规则集。已确认项目、历史规则集以及对通用规则的后续修改、删除均不会被回写，避免改变已确认的评审口径。项目内已存在分类、名称、检查规则均相同的 AI 或人工规则时不重复插入。

“重新提取规则”始终强制启动新的 AI 提取任务，不复用此前任务结果；已有待确认规则时会先在页面提示，新规则集将替换当前待确认规则集。上一版本仅由人工勾选或取消形成的启用状态不参与本轮提取，新一轮 AI 和通用规则默认全部启用；人工新增或实质修改过内容的规则仍按既有保护机制迁移，但同样重新启用。被替换的规则版本、已确认版本及历史审查结果仍保留，不会删除。

可将已启用且已配置 API Key 的模型设为全局默认模型。新建任务和页面初始选择器自动采用该默认模型，用户仍可为某一次任务临时改选；历史任务继续保存实际使用的档案 ID。删除默认模型时，系统会自动改用另一个已启用且已配置 API Key 的模型；没有可用替代项则清除默认设置。若模型正被排队或运行中的任务使用，系统仍拒绝删除。

内置 DeepSeek 预设：

- `deepseek-v4-flash`：规则提取、结构识别、错别字、客观分证据提取；
- `deepseek-v4-pro`：复杂实质性/废标审查、主观分与横向总结；
- Base URL：`https://api.deepseek.com`。

其他模型通过 OpenAI-compatible 适配器接入；每次任务可在已配置档案中选择模型。初始迁移会将已配置的 `deepseek-v4-flash` 设为全局默认模型；以后所有页面与服务端均优先使用管理员明确设置的全局默认模型，再回退至第一个可用模型。

## 准确性优先的全文覆盖与上下文控制

页面只保留“综合评审”入口。评审基线是准确性优先于 Token 节省：超过 2.4 万字符的投标文件先按页顺序切成约 1.1 万字符、相邻页有重叠的连续块，AI 必须从第一页覆盖到最后一页。全文首轮采用“证据索引”而非完整评审：每个页块正常只发送一次全部启用规则的精简目录，返回 `规则 ID、页码、短原文、支持/反向/疑点倾向、证据优先级、证据来源性质` 六项候选；不在首轮生成最终理由、建议分或 OCR 结论。只有输出截断或连续格式异常时才拆规则目录重试当前页块。较短文件直接把全文交给最终规则组。随后系统按审查、客观分、主观分小组汇总候选、补充重点章节原文并只在最终阶段形成结论、逐项业绩、计分过程和建议分。点状短语、章节标题和本地实体匹配只用于加强二次复核，不再决定某一页是否会被 AI 看到。

所有 AI 结论均由人工最终审核。提示词要求模型积极给出最可能的结论、风险、疑点、证据、理由和建议分；证据不完整或需要 OCR 时也可给出暂定判断和暂定建议分，并明确核验点。系统不再因为首轮没有候选而默认转为“需人工全文通读”，而会说明已完成全文扫描并给出“未发现相应异常/材料”或其他最可能建议。积极判断不等于允许虚构：模型不得编造原文、页码、签章、图片或线下材料，必须区分可见事实与 AI 推断。

系统为每次模型调用记录任务、阶段、模型、发送字符数、供应商返回的输入/输出/总 Token、缓存命中 Token 和上下文模式；对于规则提取和综合评审还记录请求的输出上限、服务商结束原因和响应字符数，用于定位截断，不记录提示词正文、投标文件原文、模型思考内容或 API Key。页面仅显示项目汇总，并单列图片识别调用次数、腾讯 OCR 页数（额度台账）和本地 OCR 去重处理页数（页级缓存），供评估识图预算与本地 CPU 工作量；两类 OCR 页数都不计入模型 Token。对于不返回 usage 的 OpenAI-compatible 模型，页面显示发送字符数。

全文扫描采用按需运行的工作进程，不使用向量数据库、常驻索引或本地模型。不同投标人先以两路保守并行；连续六次模型请求正常完成后，最多提升到三路，遇到 HTTP 429/529、临时过载、网关错误或超时则按三路到两路、两路到一路逐级回退并仅重试当前调用。单份文件内部仍按页块和规则组顺序执行。内存中只保留当前文件的文本块和短候选，任务结束即释放；不运行工作台时不会增加常驻 CPU 或模型资源。每个成功页块的紧凑候选会以“文件、模型、精简规则目录、范围画像、全文扫描系统/任务提示词、页块哈希”作为键立即写入工作台 SQLite；工作进程中断后可继续复用相同的已完成页块，明确强制重跑时则跳过缓存。全文覆盖不会形成常态的“页块 × 规则批次”重复扫描矩阵。

全文扫描的单个页块若返回坏 JSON，会先仅修复当次响应或在不永久改变模型档案的情况下临时禁用思考严格重试；输出达到长度上限时只拆精简规则目录，绝不递归拆分页块并重发全文。无法恢复的极少数页块不会静默丢弃，其原文会直接附入相关最终规则组二次复核。最终规则先按点状核验、数量累计、章节方案、全文一致性等证据策略归组，再以审查/客观分最多 8 条、主观分最多 6 条作为硬上限并按规则复杂度提前缩小；完成一组即持久化，单条规则最终格式异常不覆盖此前成功结果。

数量、累计和分档客观分必须尽量输出 `matched_count`、逐项证据、页码、有效性、计分过程和 `suggested_score`。后端优先采用模型在满分范围内给出的建议分；若模型已返回数量且规则含“每项/每个得 X 分”，后端可按明确公式补算并限制在满分以内。业绩结果会把数量和逐项证据整理进现有证据、理由字段，使页面、报告和 CSV 均能显示“AI 识别几项、哪些建议有效、哪些待 OCR、如何得到建议分”。需要 OCR 时暂定建议分仍保留，但不会进入自动确认状态。

规则提取采用“全文原文映射 → 分组规则编译 → 全局轻量合并 → 覆盖审计”链路，而非依赖地区、设备或评分关键词的业务补丁。主招标文件和全部招标附件不再先裁剪为固定关键词窗口，而是分别按页或段落拆成约 1.1 万字符的独立批次，并在每批重复标明文件来源，逐段映射原始条款、原文依据和页码。候选过多或输出异常时只拆当前组；各子组完成后再把紧凑规范规则做一次全局语义合并，解决跨组重复和互补信息分裂，任何全局合并故障都完整保留子组结果。评分规则同时保留 `source_clause_ids`，存在明确叶子分值时可在 `scoring.items` 中保存子项名称、分值和计扣分条件。该流程不创建常驻队列、向量库或本地模型，任务结束后释放内存，适配 2 核 2 GB 服务器；准确性优先的代价是规则提取会比旧的前置窗口截取产生更多按需模型调用。

最终规则组按任务类型限制上下文：点状核验约 4.2 万字符、全文一致性约 5.5 万字符、数量/业绩和方案章节约 6.4 万字符，防止二次汇总本身超过模型上下文。确定性检索返回 `rule_id → page chunks` 映射，缺失补评不再从所有规则共享的扁平列表顺序取页；数量/业绩和含结构化叶子项的方案规则在补评时仍可获得多个相关页块。全文扫描会为每条证据标注其对最终判断的直接性；二次汇总先保证每条规则至少有一条最高价值证据，再按价值补充其他页。相同证据页重合度高的同策略规则会优先进入同一规则组，但每条规则自身的直接页块仍被保留，不以节省 token 为由削减证据范围。若一条复合评分规则仍发生输出截断，只有当全部叶子项都有明确可加分值且其合计等于父项满分时，才按叶子项拆审并按父项满分合并；其他口径不擅自拆算。网关继续兼容模型常见的未转义换行、尾逗号、全角结构符、文本内容块和双重 JSON 编码，并按工作线程复用 HTTP 连接以减少网络握手时间。

全文范围一致性采用通用的两阶段机制。综合评审开始时，系统仅根据招标文件与已确认规则一次性生成并缓存“项目范围画像”，其中包含项目主体、工作范围、服务对象、核心任务、技术主题、设备/材料、交付物、适用标准、地域及区分度关键词。每个投标文件连续页块的首轮 AI 扫描在规则证据之外，独立返回“项目范围偏离候选”：其类型不预设为地区、项目名或公司名，可以是无关技术路线、设备材料、规范标准、服务对象、成果交付、时间地点或任何其他与范围画像不一致的内容。判断必须先区分章节的上位主题，再核对其中具体工作对象、工艺、设备材料、作业环境、标准和交付内容；“安全、施工、运维”等主题相关不代表其下所有具体内容都属于项目范围。候选仅是线索，不自行作出废标或不满足结论；模型会给出原文摘录、与范围的关系和优先级。

范围画像、偏离候选及对应原页只进入“项目范围无关/范围一致性”类规则组，避免把同一批候选重复发送给营业执照、签章等无关审查组；规则识别只用于路由，不参与异常结论。范围候选不依赖评审规则目录单独稳定缓存：同一文件页块在旧轮发现的中高价值候选，可在规则变化或强制重跑时作为“待复核线索”继续交给本轮 AI，但绝不直接继承旧结论。系统会过滤模型误放入异常数组的“与项目一致、合理出现、未发现偏离”等正常项；注册地址、联系地址、业绩、公司介绍、合理引用及可选方案不会仅因内容不同被自动认定异常。最终是否构成问题仍由 AI 结合当前范围画像、规则及原页重新提出建议，并保留给人工审核。

MiniMax M3 的全文扫描、审查和客观评分临时禁用思考，以提高严格 JSON 稳定性；主观方案评分仍保留自适应思考，模型档案的默认设置不会被永久改变。模型若只发生 JSON 语法或转义异常，系统先把当次短响应交给独立、可配置的“结构化结果修复”提示词，不重发数万字投标文件；输出确实达到长度上限时才拆小当前规则组。规则组只漏回部分规则时，仅补评缺失规则，已有结果不重算。以上重试都不把响应正文写入数据库或日志。

任务结果将分别记录 JSON 修复次数、严格紧凑重试次数、规则组拆分次数和缺失规则补评次数；“格式恢复次数”仅作为兼容旧结果的汇总字段，不能再被理解为紧凑重试次数。为降低 MiniMax M3 在长上下文下的 JSON 格式异常，全文扫描的范围偏离候选只保留页码、开放类型、优先级、原文短摘录和与项目范围的直接关系；最终审查与评分仍保留原文证据和判断，但要求理由使用一条短句，不重复叙述已有证据。

最低价、评审价、基准价、价格分或报价得分等必须跨投标人计算的客观规则，不进入单份文件评分组，避免产生无法横向比较的临时分数。全部投标文件就绪后，系统一次性提取并比较报价相关页，核对口径、币种、最高限价和异常报价后计算建议分；格式失败或漏回某家公司时明确保存“暂无法计算”，不得留下单文件阶段的不可靠分数。该流程按需运行，不引入常驻服务，提示词可从页面右上角查看和修改。

右上角“提示词配置”按维护频率分为三级：最上方“常用业务指令”集中展示文件查重、评审规则和综合评审的通用判断原则，默认展开并推荐优先修改；“业务流程细节”包含规则映射/编译/覆盖审计、全文扫描、审查与评分等专项模板，默认折叠并提示必须保留字段和运行时变量；“系统与结构模板”包含模型测试、系统角色、综合评审结果结构通用约束、JSON 修复及旧流程兼容模板，默认整体折叠。通用结果约束要求证据、计分过程和理由不复述页面已单列的检查规则。分组只影响界面展示，所有模板仍可查看、编辑和恢复默认，不改变现有接口或模型调用行为。

综合评审默认自动复用完全相同输入的已完成任务。统一执行指纹覆盖主招标文件、招标附件、投标文件、解析状态、规则集、模型公开配置与全部提示词，不包含正文或密钥；最终审查与评分结果仍绑定该完整指纹。范围画像和全文扫描缓存改为仅绑定自身实际依赖的资料、规则、模型及对应提示词，因此只调整主观评分或结果表达提示词时，不会重做已完成的范围画像和全文扫描。API 的 `force_rerun=true` 会同时跳过整任务、单份投标文件和全文扫描缓存复用，确保用户明确要求重新判断时一定重新调用。新增投标文件时，未变化文件仍可按同一完整指纹逐份复用。AI 查重同样复用完全相同输入的完成结果，且其模型请求仅记录压缩证据包的字符数，不保存证据正文。

## 新建项目口令

新建项目必须在页面输入口令。当前部署可在运行环境的 `.env` 中设置 `EVALUATION_WORKBENCH_NEW_PROJECT_PASSWORD`，服务端仅在内存中读取并与请求值作恒定时间比较；不写入数据库、日志、前端代码或仓库。为兼容既有部署，仍支持 `EVALUATION_WORKBENCH_NEW_PROJECT_PASSWORD_HASH`（Werkzeug 密码哈希）；若两者同时存在，明文运行环境配置优先。未配置时服务端拒绝创建项目并返回明确提示。

## 规则来源与确认

AI 从招标文件提取的规则会直接写入当前项目的“待确认规则集”，在规则表中逐条标记为“AI 提取”；人工新增的规则逐条标记为“人工补充”。人工修改 AI 规则的检查语义、评分口径或启用勾选后会标记为“人工锁定”。重新提取时仅刷新普通 AI 规则，人工补充和人工锁定规则会迁移至新草稿，避免重新提取静默删除人工维护结果或重新启用已取消勾选的规则；AI 规则仅是待确认建议，不能绕过人工确认直接用于审查或评分。

## 任务机制

使用 SQLite 任务表与按需启动的单一 Python 工作进程，不引入 Redis、Celery 或常驻任务容器。工作进程按顺序领取任务，队列为空即退出。项目轮询只传输任务摘要，不重复传输大型 `result_json`，详细结果由专门结果接口按需读取。状态为：排队中、运行中、已完成、失败、已取消、上次运行中断。

项目删除仅在没有排队或运行中任务时允许执行；会同时删除项目的 SQLite 记录、原始上传文件、解析缓存、查重结果、审查结果、评分结果和项目报告目录，以回收服务器磁盘空间。删除前必须由用户在页面确认，且不可恢复。

## 结果一致性、查重价值与长文扫描治理（2026-07）

综合评审的文字、OCR、图片识别与跨投标人价格核验属于同一条证据链，但各阶段完成时间不同。为避免后完成的事实与早期结论并列造成误导，系统遵循以下稳定性约束：

- 跨投标人价格核验已经定位到同一投标文件的明确报价金额时，单文件审查中仅以“未见报价/金额”为依据的结论会降为“部分核验”，撤销该缺失表述；不会据此自动认定符合最高限价或自动改变价格分。
- 对只有一个明确封顶评分项的数量型材料（例如“每提供一项业绩、最多 N 分”），若图片识别已在实际证据页确认材料并返回临时材料 ID，后端可以在封顶内同步更新建议分；多叶子规则仍须严格按规则 ID 汇总，防止串分。
- 页面主表只展示一条关键证据、简短理由和 OCR/图片核验状态；完整文字结论、OCR/视觉分层证据均保留在折叠区，既不丢失审计链，也不让逐页转写淹没结论。
- 重要结论提炼只能消费完成校正后的结果；报价、OCR 和图片的旧阶段“未见/待核验”表述不得作为独立高风险事实。

文件查重采用“招标原文过滤 → 公共格式过滤 → 信息量排序 → AI 复核”的四层口径。除已加载招标原文外，还会通用识别封面、投标函、授权/法定代表人文件、项目/采购人/投标人等格式字段，以及招标表单中填写或删除占位符的正常操作；这些内容不进入 AI 串标线索。表格抽取造成的编号、标点异常也不作为共同错误。保留并优先展示招标原文之外的技术参数、专有方案、实质数值变化、罕见正文错误和敏感实体。AI 已排除的维度不再抬高文件对的复核优先级。

长文件全文扫描继续保持按页块从第一页到最后一页的覆盖，不以降低准确度为代价跳页。为减少 MiniMax 等模型因长 JSON 输出截断导致的拆分重试，正常页块最多返回 24 条紧凑候选和 6 条范围候选；最终规则组仍拥有本地章节召回和原页复核兜底。候选排序优先级为投标人自主方案、投标人承诺、未知来源、招标原文复述、表单模板；后两者仍可被最终模型识别为“仅复述”，但不能挤占真实证据的上下文。

项目、文件解析、多文件查重、规则中心、综合评审、评分、浏览器打印报告与 CSV 导出三个既定阶段均已完成。XLSX、DOCX 报告会在不引入常驻重型依赖的前提下作为后续兼容性扩展。

## 评审稳定性、断点续跑与缓存观测（2026-07）

综合评审以“调用级恢复、规则组级隔离、结果级复用”三层保障长任务稳定性。模型发生短暂断连、读取超时、连接重置或可恢复的 5xx/限流时，仅重试当前调用，采用 5 秒、15 秒、45 秒退避；鉴权、参数等不可恢复的 4xx 错误仍立即返回，避免掩盖配置问题。连续恢复失败的规则组不再终止整项任务：已完成组照常持久化，失败组以明确的待重跑项记录在任务结果中，页面可选择“仅重跑失败项”。

仅重跑失败项的复用键由项目、规则集、投标文件和完整执行指纹共同组成。成功的单规则结果写入 SQLite 快照；重跑时只复用同一指纹下的成功规则，失败规则的人工兜底结果不会写入快照，并会清理同键旧快照，防止把“待重跑”误当作已完成。该机制不改变既有审查、评分和任务 API 的字段含义，也不增加常驻进程或内存占用。

为避免重复评分和相互矛盾的呈现，规则提取阶段会在“同一来源条款 ID（或同一明确原文依据）+ 同一评分对象 + 同一满分”时合并标题差异仅为“满分 X 分”的重复评分规则，保留评分叶子项、检查条件和原文更完整的版本；不会仅凭相同标题跨来源合并。图片/OCR 复核导致建议分调整时，最终理由以“最终建议分”为准，不保留与建议分冲突的旧计分推导；一般性“建议 OCR 复核”等套话不再重复占据结果正文，只有确有未决关键证据时才保留。

同一任务中，单份投标文件的明确总报价、招标文件唯一明确的最高限价/预算及其保守对比结论会形成最小共享事实包，供符合性审查和客观价格评分共同引用，避免一侧已经确认金额、另一侧仍写“未见报价”。该事实包只来自本地可定位文字，不会擅自计算价格分或改变评分口径。

提示词中的规则目录、范围画像和结构化参数采用固定 JSON 键序，减少无意义的前缀变化，便于 DeepSeek、MiniMax 及其他兼容服务商在支持时命中其上下文缓存；不调整用户可配置提示词的业务顺序或变量协议。模型调用台账除项目总缓存命中 Token 外，新增按调用阶段的缓存汇总，页面展示总体命中率。后续只有在真实云端台账证明某一环节稳定具备高命中空间时，才评估更激进的提示词前缀重排；不得为节省 Token 改变全文覆盖、证据范围或已有提示词语义。

OCR 结构化归纳失败时，页面证据中的原文兜底只做展示级压缩：明显的逐字断行表格表头会折叠，金额、数量、型号、编号、日期和单位等短值必须保留。原始 OCR 页缓存、传给模型的 OCR 正文和审计证据不做删改。文字、OCR 与图片层合并理由时，只消除去除识别层前缀、空白和标点后完全相同的句子；不同的计分过程或判断依据均保留，避免以“去重”掩盖真实冲突。主观评分默认提示词要求非满分必须列出至少一项可定位的具体差距或扣分依据。

缓存前缀重排是后续候选阶段，尚未实施。2026-08 云端存量台账显示全文扫描约 12% 缓存命中，而最终审查/评分规则组约 3%，说明确有优化空间；但当前最终组没有一份可直接复用、且不会重复注入全文证据的稳定文件摘要，因此现在重排反而可能增加输入量或改变模型注意力。必须先在不参与结论的影子路径生成稳定摘要，再以默认关闭的开关 A/B 对比“稳定系统指令→项目范围画像→文件稳定摘要→当前规则组→当前证据包”，同时验收规则覆盖率、结论一致性、格式异常次数、耗时和 Token。不得自动改写用户提示词，也不得为了缓存率重复发送全文或全量规则。

全文扫描新增输出风险影子台账：每次调用只根据规则数量、规则目录长度、页块字符数、复杂评分规则数量和请求输出上限计算风险分，并记录模型是否真的发生格式异常、结束原因及实际恢复路径；不保存正文或模型输出。该分数当前不参与预拆分、Token 上限或重试决策，因而真实执行行为与上线前一致。只有累计至少 300 个观测、覆盖不少于 3 个结构差异明显的项目和 2 类模型，且高风险预测对格式异常的召回率不低于 85%、误拆建议率不高于 15% 时，才允许进入小比例灰度；灰度仍需证明总耗时下降且规则召回、最终结论和失败率不劣于基线，否则继续保持影子状态。

## OCR 与多模态独立运行（2026-08）

OCR 文字取证和多模态图片外观取证是两套独立能力。全局模型配置分别提供“在评审中启用 OCR 文字取证”和“启用多模态图片外观识别”两个开关：前者开启后可优先使用腾讯云 OCR，额度、凭据、接口或服务异常时自动回退至按需启动的 RapidOCR；后者开启后才允许向已标记为多模态的模型发送图片。关闭多模态绝不关闭 OCR，因而 DeepSeek V4 Flash 等纯文字模型可以完成“全文文字审查 + OCR 文字补充 + 最终建议”；关闭 OCR 也不妨碍多模态模型独立检查签章、勾选状态、版式、照片或材料外观。

规则执行元数据新增可选 `image_mode`，取值为 `auto`、`ocr_only`、`vision_only`、`combined`、`off`。旧规则没有该字段时统一按 `auto` 运行，原有 `vision_trigger`、`vision_level` 字段和外部 API 不变。`ocr_only` 严格不发送图片给模型；`vision_only` 不发送 OCR；`combined` 在同一规则中保留 OCR 与多模态两类事实，证照/截图等可先由多模态定位再 OCR 核对字段，扫描文字/表格可先 OCR 筛选再按需视觉复核。纯视觉事项在多模态关闭或不可用时必须显示未完成，不能用 OCR 文字冒充已核验。

任务启动不再因为存在图片规则而要求主评审模型具备多模态能力，也不因没有默认图片模型拒绝整个综合评审。缺少某一种能力时，其他规则和可用通道照常执行；无法执行的图片外观规则在单条结果中明确说明。结果内部新增 `ocr_status` 与 `multimodal_status`，同时继续保留历史 `vision_status` 字段以兼容网页、报告和外部调用。OCR 和多模态证据分别留在证据层，字段冲突不得静默覆盖，需并列提示人工复核。

验证基线包括：纯文字模型 + 腾讯 OCR、纯文字模型 + RapidOCR、OCR 失败保留文字结论、纯 OCR 规则没有多模态模型仍可排队、纯多模态、OCR + 多模态组合、腾讯额度耗尽回退、图片模型过载不丢失 OCR 证据，以及历史规则/结果/API 的回归测试。RapidOCR继续使用单路短生命周期子进程，图片模型请求保持单路门控，适配腾讯云 2 核 2 GB 环境；不运行任务时不常驻加载 OCR 或视觉模型。

## 复合规则的逐项取证（2026-08）

规则提取可以把同一主题下的多个叶子要求合并为一条便于人工阅读的父规则，但合并展示不能把多个独立证明材料混成一个取证对象。为此，提取提示词允许在父规则中附带可选 `evidence_items`：每项仅保存叶子名称、需核验的事实、原文页码和证据维度。它不是子规则，不单独启用、不单独计分，也不改变父规则的原文后果或最终结果 API。

综合评审中，只有存在两个及以上已结构化子项的规则才启用逐项取证计划：本地候选页定位会分别使用每个子项的材料锚点，并采用轮转顺序，让每项优先获得至少一个候选机会；随后仍保留父规则原有候选页，避免因子项定位不完整遗漏旧链路证据。标准/高强度下可在受控范围内适度提高复合规则的 OCR 或图片首批页数（OCR 最多 8/12 页，图片首批最多 6/8 页）；低强度和没有子项的规则保持原上限。图片后续补页、单路门控、RapidOCR 短生命周期和结果合并逻辑均不变，保证 2 核 2 GB 环境不出现无界并发或常驻内存增长。

前台“智能取证”与“每次都取证”的差异只在启动条件，不在强度或通道：智能取证先看全文文字，仅在文字不足、扫描件疑似或规则确需外观事实时启动图片取证；每次都取证则即使文字已充分，也会对定位到的候选材料额外启动一次取证。二者均继续由规则和全局能力选择 OCR、图片模型或二者组合，且都受所选强度的页数上限约束。执行预览必须显示该差异；复合规则还显示“按子项轮转覆盖”的说明。

## 本地 OCR 基线与增强核验（2026-08 修订，已实施）

本节取代本文此前“腾讯优先、本地回退”“OCR 总开关可关闭”及“视觉优先后再 OCR”的运行优先级描述；历史字段、旧接口和既有结果仍保持兼容。

1. **固定基础层**：本地 `RapidOCR / PP-OCRv5 mobile / ONNX CPU` 是工作台固定能力，不再作为可关闭开关；“固定”仅表示能力始终可用，不表示每条规则必定调用。只有规则明确需要 OCR、文件为扫描型、或全文文字结论不足以支撑判断时，才处理已由全文解析、目录、规则材料锚点和 EvidencePack 定位出的有限候选页；文字证据已充分的普通材料/字段规则不重复 OCR，绝不因此对整份 PDF 逐页 OCR。运行仍采用全局单路、短生命周期子进程、页级缓存和任务结束释放内存的模式，适配 2 核 2 GB 服务器。
2. **可选增强层**：腾讯云 OCR 仅用于本地 OCR 已定位的证照、证件、关键字段、低置信或基础识别不完整页面；多模态仅用于签章、勾选、外观、版式等视觉事实，或规则明确要求图片复核的材料页。腾讯服务、额度、凭据或网络不可用时保留本地文字；本地运行环境或子进程发生异常时，只要腾讯已启用且凭据可用，即使规则选择“仅基础识别”也会将腾讯 OCR 作为一次容错路径。两者都不改变全文文字审查、原有结果字段或失败恢复机制。
3. **统一执行顺序**：全文文字审查 → 本地 OCR 基础取证 →（按规则策略）腾讯 OCR 精确字段复核 / 多模态外观复核 → 原有 OCR/图片结果合并。腾讯或多模态结果成功时仅覆盖同页的文字来源或补充视觉事实，不把两份原文重复发送给模型；任何增强失败都不覆盖基础结论。
4. **规则交互**：原“图片取证”统一展示为“增强核验”。“不作增强核验”表示不追加腾讯或多模态，且仅在明确需要/扫描型文件/文字证据不足时使用本地 OCR；“智能升级”表示仅在关键字段、识别不足或外观事实需要时升级；“每次都升级”表示每次评审均追加一次增强核验。旧 `image_mode`、`vision_trigger`、`vision_level` 继续存储与返回，专家模式仍可限定增强通道，不影响外部 API。
5. **候选页与可追溯性**：本地 OCR 实际处理页作为多模态的低优先级后备候选；目录显式页、直接证据页和 OCR 明确证据页保持更高优先级。页面仍区分“检查页”和“证据页”；客观分仅显示材料类别、数量、有效性、页码、计分结论和未决项，不展示 OCR 原文。

高强度规则若本地解析文本无法给出可靠候选页、但系统已配置多模态模型，允许仅调用一次低清联系表用于**找页**，随后仍由本地/腾讯 OCR 识别文字；专家选择“腾讯 OCR”并不会因此失去纯扫描件找页能力。找页模型失败或不可用时只保留原候选链和原文字结论，不中断任务。原先的“视觉优先→后置 OCR”链路已移除，统一遵循“本地 OCR 先行、增强层后续补充”的顺序，避免两套链路互相覆盖。

验证要求：已覆盖旧 OCR 配置 API 的兼容请求、本地先行与腾讯覆盖关键页、腾讯关闭时本地独立运行、本地不可用时腾讯容错、充分档纯扫描件找页、纯文本模型与图片模型的独立运行，以及 JavaScript 语法与全量工作台回归。未来若新增 OCR 或多模态服务商，必须只接入能力适配层和统一证据协议，不得在规则/评分业务层写入 MiniMax、腾讯或其他服务商的专属判断。

### 规则级基础核验路由（2026-08）

规则执行元数据新增向后兼容的 `baseline_ocr_mode`：`auto` 表示按 AI 提取出的证据类型和本轮文字结论动态判断，`text_only` 表示人工明确限定为纯文字，`local_ocr` 表示人工明确要求执行有限候选页本地 OCR。旧规则缺少该字段时仍按 `auto` 运行，不迁移数据库、不改变既有 API 字段含义。

规则提取、续提、规则编译与覆盖审计必须全程保留 `evidence_requirements`，防止分段编译后证据类型丢失并回退到宽泛关键词。默认路由以决定性证据为准：纯文字/表格规则采用 `auto` 的文字优先路径，正常机器可读时不 OCR，只有整页扫描导致文字覆盖不足时才补识别有限候选页；材料存在性或编号、日期、金额、型号等字段规则同样采用 `auto`，全文证据充分时跳过 OCR；只有签章、勾选、手写、指印和版式外观等必须看图的事实才标记为强制图片路径。证书、报告、复印件或扫描件只是材料名称/载体，不得单独导致整条规则每次 OCR。`text_only` 只代表用户人工明确禁止 OCR，不由 AI 提取默认强制设置，以免漏读扫描型技术方案。

规则页面的主下拉统一为“核验方式”：默认“按 AI 建议”，并保留“文字优先（必要时本地 OCR）”这一不使用外部增强的兼容路径，同时允许人工明确选择“纯文字核验”“本地 OCR 核验”“智能增强核验”“每次都增强核验”。前三种人工基础路径不会调用腾讯 OCR 或多模态；后两项才使用增强通道和强度预算。综合评审任务结果新增本地 OCR 实际执行规则数、跳过规则数、累计耗时及增强规则数，用于部署后直接判断 OCR 是否仍是耗时主因，不保存正文或密钥。

## 2026-08-03 本地 OCR 常驻 worker 改造（方案A）

### 背景
- 原模式每批页面都新建 RapidOCR 子进程并重载 ONNX 引擎：云端实测单批固定开销约 4 秒，

- 全局单执行位（`_LOCAL_OCR_REQUEST_GATE=1`）是防 OOM 的必要保护：单子进程峰值 500-650 MB。

### 改造
- `rapidocr_worker.py` 新增 `--serve` 常驻模式：引擎只加载一次，stdin/stdout 逐行 JSON 协议；
  单批失败不退出，stdin 关闭即退出。原单次模式保持不变。
- `local_ocr_gateway.py` 重写：`_ServePool` 常驻进程池 + 懒启动 + 空闲 300 秒自动回收（守护线程）
  + atexit 关闭；任何启动/通信/超时异常自动回退逐批短进程（`subprocess.run`），行为与旧版一致。
  `RAPIDOCR_WORKER_MODE=oneshot` 可临时禁用常驻模式。
- 并行度可配置：`LOCAL_OCR_MAX_WORKERS`（默认 1，上限 4）同时约束 gateway 池大小与
  worker.py 的 `_LOCAL_OCR_REQUEST_GATE`。2GB 服务器保持 1；内存升级到 4GB 以上可设 2。
- 遥测字段（elapsed_ms/peak_rss_kb/recognized_pages 等）与 `record_local_ocr_run` 台账不变。


### 单路 OCR 进一步提速（2026-08-03 补充）

- `_render_ocr_page` 新增任务级渲染缓存：同一任务内同一页同一档位的 JPEG 只渲染一次，
  与图片模型链路共用 `_VISION_TASK_RENDER_CACHE_BYTES` 容量上限和 FIFO 淘汰，只缓存字节。
  多条规则命中同一候选页时不再重复 fitz 渲染，节省 2 核 CPU。
- OCR 子进程数值库线程数改为 `RAPIDOCR_OMP_THREADS` 环境变量（默认 1，上限 4）：
  单路 OCR 且评审其余环节多在等待网络时，可设 2 让 ONNX 推理用满双核提速。
- 既有调优杆：`RAPIDOCR_LIMIT_SIDE_LEN`（640-1280，默认 960）降低可提速检测但有小字风险。
- 未采纳项：本地渲染分辨率与检测输入 960 对齐可再省渲染 CPU，但会改变图片哈希、
  使历史页级 OCR 缓存全部失效一次，收益小于代价，暂不实施；`Rec.rec_batch_num` 在
  rapidocr 3.8.1 的参数键无法可靠确认，为避免设置后破坏 OCR 未纳入。


## 核验方式"AI 建议"依据链（2026-08-03 审阅优化后定稿）

规则确认界面的"系统建议"（off/smart/visual）不是模型直接选通道，而是三层依据链：

### 第一层：提取模型的语义判断（主要依据）
- 提取/编译提示词要求模型为每条规则输出 `evidence_requirements`（text=文字表格、
  document=材料本体、field=编号/日期/金额/型号等字段、visual=签章/勾选/手写/版式/扫描图片外观、
  cross_bid=横向比较、external=外部核验）和 `ocr_required`。
- 硬性约束：只要已解析文字可能完成判断就必须包含 text；不得仅因材料名含
  "证书、报告、复印件、扫描件"就设 ocr_required=true；只有决定性证据是机器可读文字
  无法承载的视觉事实时才允许 true。

### 第二层：代码兜底归一化（模型漏给/乱给时）
- `_normalise_visual_rule_policies`：模型未返回证据维度时，用执行级正则
  `DECISIVE_VISUAL_FACT_PATTERN`（签字/签章/盖章/公章/印章/骑缝章/手写/指印/勾选/涂改/外观类，
  只扫 check_rule）兜底为 visual 或 text；document/field 自动补 text；
  ocr_required 仅当 visual 是唯一证据或命中决定性外观词。
- 该层只保留 AI 判断作为建议元数据；执行开关（acquisition_preset/image_mode/vision_*）
  一律默认 off + baseline_ocr_mode=auto，是否升级由人工逐条选择。

### 第三层：建议档位确定性映射（`rule_acquisition_recommendation`）
- visual 证据或文本命中统一建议词汇表 `RULE_VISUAL_SUGGESTION_TERMS`
  （执行级词汇全集 + 图纸/截图等图像载体词）：同时需要文字/字段 → smart（智能取证），
  纯外观决定性 → visual（必须看图）。
- 一致性护栏：check_mode=ocr 或 ocr_required=true 的规则建议不低于 smart，
  避免"模型判定需要 OCR、系统却建议仅基础识别"的自相矛盾。
- 其余 → off（仅基础识别）；baseline_ocr_mode 恒为 auto（本地 OCR 基础层不参与增强建议）。
- 建议逐条实时计算、只展示不改写；词汇表通用，不为行业/证书/项目写补丁；
  执行级词汇 ⊂ 建议级词汇，保证两层结论不会反向矛盾。

## 2026-08-04 评审准确性与进度口径三项通用修复

### 1. 综合评审进度分母纳入基础 OCR 规则
- 问题：本地 OCR 基础化后，启动方式为关闭的规则也会因基础 OCR 在视觉循环中
  推进进度，但分母 `visual_rule_count` 只按增强规则估算。实际推进数可达估算
  5 倍，进度提前封顶 100%，剩余 OCR 批次仍刷新"正在本地 OCR"中间态文案。
- 修复：新增 `_visual_advance_estimated` 静态上界估算——增强规则必计入；
  baseline_ocr_mode=local_ocr / ocr_required / check_mode=ocr 必计入；auto 模式
  且规则元数据含 document/field/visual 证据需求、材料角色或 ocr/hybrid 图像策略
  的按"可能执行"计入。宁可进度略滞后，也不提前到 100%。

### 2. 价格公式识别与回填理由口径
- 问题一：`_price_formula_kind` 的最低价基准正则要求"最低…价"紧邻，识别不了
  "投标价格最低的投标报价为评标基准价"这类最常见表述，导致确定性价格分未复算。
  修复为允许"最低"后 8 个汉字内出现报价/价格/价。
- 问题二：唯一总报价回填的理由原文写"已参与统一公式复算"，但公式不适用时
  实际未复算，理由与空分数自相矛盾。修复：回填理由只陈述回填事实；公式未达
  自动复算条件时追加"价格分需人工核对"；复算成功时理由仍含完整计算式。

### 3. 重新提取跳过与人工修改版同名同分的评分规则
- 问题：`replace_rules_from_extraction` 保留 ai_edited/manual 规则后，新 AI 规则
  按"标题+检查规则"签名去重；人工改过检查规则后签名不同，同一评分条款被重复
  插入，综合评审重复计分且两次结论可能互相矛盾。
- 修复：保留规则先建立（类别, 评分对象名归一化, 满分）软键集合，新 AI 评分规则
  命中即跳过——人工修改版就是用户对同一评分事实的策展版本。复用预检同款
  `_score_rule_title_core` / `_score_rule_max_value` 口径，对象名 <4 字或无有效
  满分不参与，避免误并。

## 2026-08-04（二）分数回溯与汇总结论修复

### 1. 理由分数回溯兜底（`_score_declared_in_text`）
- 问题：模型把明确建议分写进理由/计分过程（如"结果=14分，封顶14分"）却漏填
  结构化 suggested_score 字段，导致分数栏为空、理由里却写着分。
- 修复：`_suggested_score` 末尾统一接回溯——只取"最终/建议/得分/合计/总计/封顶"

  由人工核对，不把猜测当结论。客观分与主观分共用同一兜底。

### 2. 汇总结论（highlights）输出截断
- 问题：投标人多（如 8 家）时结论 JSON 输出超过 4000 token 上限被截断，

- 修复：输出预算改为 min(8000, 1400 + 投标人数×600) 随人数放大；

  仍失败才保留原始结果并计数。

## 2026-08-04（三）文件下载与查重误判修复

### 1. 文件中心源文件下载

### 2. 15 位纯数字长串误判"人员身份信息"

### 3. "共同改动"两类对齐假象
- 插入侧截断假象：招标比较单元在换行/分页处截断（如"…通过手势"戛然而止），
  投标文件持完整句子时，招标原文自己的后半句被误判为两家"共同新增"。

  方向相反、逻辑对称——删除侧查投标全文，插入侧查招标全文

  截断点锚点（前 6 字/后 6 字、16 字窗口）才判为假象；真实新增在招标全文中
  不存在，信号完整保留。
- 表格拼接假象：PDF 提取把"数量 13套"与下一行序号"8系统软件"拼成

  `_is_low_value_tender_edit` 新增"数量单位（台套件项个张把批块组辆架部）后
  紧跟数字序号"的拼接特征识别；不与"年/月/日"等时间单位冲突。
- 两处过滤器接入 `_shared_tender_edit_evidence` 统一过滤链，exact/fuzzy
