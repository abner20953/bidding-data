# 跨 AI 协作与文档维护规范

## 1. 目标与边界

本规范保证 Codex、其他 AI 开发工具和人工开发者在上下文不连续时，仍能从同一事实入口继续工作。文档承担“规则、基线、当前状态和索引”，不承担完整提交历史、运行日志、原始诊断数据或密钥存储。

除根目录 `AGENTS.md` 作为工具自动发现入口外，工作台 AI 协作文档和校验脚本必须集中在本目录，禁止在仓库根目录或其他目录新增内容重复的 `CONTEXT`、`HANDOFF`、`MEMORY` 文件。某工具确实要求专属入口时，该入口只能链接本目录，不得复制规则；新增前须用户确认。

## 2. 四类文件的唯一职责

| 文件 | 只负责 | 禁止写入 |
|---|---|---|
| `AI_CONTEXT.md` | 阅读入口、事实来源、任务路由、最小闭环 | 当前进度、实现历史、长篇架构 |
| `评标工作台设计.md` | 长期产品/业务/架构契约、稳定核心、验收与未来门槛 | 动态状态、逐次修复、提交清单 |
| `AI_HANDOFF.md` | 当前未完工作、已验证事实、风险、下一动作和回退点 | 已完成历史、长期规则副本、密钥 |
| `协作与文档规范.md` | 文件职责、更新/移交/校验规则 | 当前任务内容和业务实现细节 |

同一事实只在一处完整描述，其他文件只链接。代码和测试是当前行为的最终事实；文档不得通过复制大量代码来“保鲜”。

## 3. 篇幅与简洁度预算

| 文件 | 建议行数 | 硬性范围 | 写作要求 |
|---|---:|---:|---|
| `AI_CONTEXT.md` | 50–80 | 40–100 | 只保留入口、路由、事实来源和不可越界约束 |
| `AI_HANDOFF.md` | 40–80 | 30–100 | 只保留仍影响下一步的状态，活跃记录最多 10 条 |
| `评标工作台设计.md` | 320–450 | 280–500 | 只保留长期契约、稳定核心和未来门槛 |
| `协作与文档规范.md` | 60–90 | 55–120 | 只保留协作规则和校验方法 |

- 新内容必须带来新的长期事实、当前风险或可执行动作；否则不写。
- 同一结论只在一个文件完整说明；三项以上并列关系优先使用表格或列表，不复述成多段文字。
- 一段只表达一个判断；标题下超过 6 个同类要点时，应合并、分组或删除已失效项。
- 更新必须“替换旧口径”，不能在末尾追加日期日志；超过建议行数时先删重复、已完成记录和实现细节。
- 校验脚本检查硬性范围和结构；“是否啰嗦”仍由修改者在提交前人工复核。

## 4. 接手协议

1. 先读根 `AGENTS.md` 与 `AI_CONTEXT.md`，再按任务路由读设计，最后读交接。
2. 检查 Git 工作树、分支、HEAD、远程状态和相关提交；不要把交接里的旧值当成自动可信。
3. 需要诊断云端时，核对任务实际代码版本、提示词指纹、模型档案、规则集版本和文件哈希；仓库默认值不能代表云端自定义配置。
4. 区分用户已有改动、前一位未提交改动和本轮改动；不得覆盖不属于本轮的内容。
5. 明确修改层和不变契约。业务口径或工作流不清楚时先向用户确认。

## 5. 修改原则

- 先复现、再定位最早出错层、再写失败测试、最后修改；禁止从页面症状直接堆兜底。
- 单轮尽量只改变一个责任层。必须跨层时，拆成可单独验证和回退的步骤。
- 案例只能用于抽象通用性质和建立测试夹具，不能进入生产分支、关键词白名单或默认提示词特例。
- 提示词适合语义口径；代码适合身份、来源、结构、状态、分值守恒、缓存、恢复和兼容。不得用正则代替开放语义判断。
- 无基线数据时，不宣称“更快、更准、更省”；写明尚待验证。

## 6. 设计文档何时更新

必须更新稳定设计：产品范围、业务口径、默认工作流、受保护核心、主流程阶段、数据/API 状态含义、规则/证据/缓存身份、OCR/模型职责、提示词契约、黄金项目或未来阶段门槛发生长期变化。

不更新稳定设计：不改契约的普通 bug、样式、文案、日志、函数名、局部重构、原始 JSON、长 diff、单项目诊断、一次网络/过载故障、普通提交部署记录。通用回归案例进入测试，代码细节进入注释，历史进入 Git。

修改稳定设计时替换旧口径并删除失效内容，不并列保留互相冲突的新旧方案。设计正文上限 500 行；接近上限时先合并重复和删除过时内容。

## 7. 交接记录协议

- YAML 头必须保留既定字段；未知值写 `unknown`，不得推测。更新交接时同步 `updated_at`、`base_commit`、`working_tree` 和用户授权范围。
- 活跃记录最多 10 条，只保留仍影响下一位的重要事项。相同工作流动态更新一条，不按日期机械追加。
- 每条写：目标/状态、范围、不变契约、验证、剩余动作、风险、主要文件或回退点。
- 已完成且不再影响决策的事项从交接删除；长期决定合并到设计；详细过程留在 Git。
- 用户授权必须精确记录。分析授权不等于修改，修改授权不等于提交，提交不等于推送，推送不等于部署。

允许的 `status`：`local_changes`、`tests_pending`、`ready_for_commit`、`repository_synced_cloud_unverified`、`deployed_validation_pending`、`blocked_user_decision`、`clean_no_active_work`。

## 8. 配置漂移协议

- 仓库默认提示词与云端自定义提示词是两层事实；任务结果应按实际模板 ID/指纹判断，不按本地默认文本猜测。
- 模型配置、通用规则和 OCR 开关同样以任务快照或云端实际配置为准。
- 页面蓝点、部署记录和任务运行版本不一致时，以任务运行时/容器 build-info 为诊断起点，并显式记录差异。
- 任何文档只记录“已配置/未配置”和版本指纹，不记录 API Key、SecretKey、Token、密码或 Cookie。

## 9. 交付与校验

代码任务至少执行相关定向测试、工作台完整回归与 `git diff --check`；具体命令见稳定设计第 9.3 节。文档任务运行：

```powershell
python docs/ai协作/validate_docs.py
git diff --check
```

校验脚本只检查文档结构和明显漂移，不能替代人工审阅、测试和云端验收。未经用户确认，不提交、不推送、不部署。
