# 工作台设计与开发基线

更新时间：2026-08-17

适用模块：`/pingbiao`、`/api/evaluation-workbench` 及 `dashboard/evaluation_workbench/`

文档性质：稳定的产品、架构与验收基线

## 0. 如何使用本文档

本文档不再记录逐次修复过程。它只回答五件事：

1. 工作台要解决什么问题，明确不做什么；
2. 当前生产设计和关键数据契约是什么；
3. 开发时必须遵守哪些约束；
4. 哪些未来改造已规划、满足什么条件才能启动；
5. 哪些稳定核心必须保护、未来改造满足什么条件才能启动。

协作入口、事实来源和冲突处理统一见同目录 `AI_CONTEXT.md` 与 `协作与文档规范.md`。若本文档与当前代码不一致，不得任选一方继续开发：先用测试、运行数据和 Git 历史确认真实状态，再修正代码或本文档。

本文档使用三种状态：

- **已实施**：当前代码存在且已有测试；是否部署以同目录 `AI_HANDOFF.md` 和云端运行时版本为准。
- **计划中**：已有方向和门槛，尚不能作为现行行为依赖。
- **禁止**：后续开发不得采用，除非用户明确改变基线。

任何 AI 接手本模块时，应先从同目录 `AI_CONTEXT.md` 开始，按任务路由读取本文档相关章节。详细历史从 Git 获取，不把提交日志重新复制回本文档。

## 1. 产品目标与边界

### 1.1 目标

“工作台”是面向单人、低并发场景的招投标评审辅助模块，主要能力包括：

- 管理评标项目、招标文件/附件和多份投标文件；
- 解析文件并建立可追溯的页级文本；
- 对多份投标文件做本地候选筛查和 AI 查重复核；
- 从招标文件提取、编辑、选择并确认评审规则；
- 对每家投标文件完成审查、客观分和主观分建议；
- 按需使用本地 OCR、腾讯 OCR 和多模态模型补充图片证据；
- 提供网页、打印报告和 CSV 结果。

所有结论都是 AI 建议，最终由人工审核。准确性和可追溯性优先于 Token 节省。

### 1.2 明确不包含

- 投标文件或技术方案编写；
- 自动作出法定串标、废标或最终得分决定；
- 多用户协同、审批流或复杂权限系统；
- 常驻本地大模型、GPU 服务或向量数据库；
- 在展示层重新推导业务结论；
- 为单一项目、投标人、设备、金额、页码或年份编写生产补丁。

### 1.3 独立性

- 页面入口为 `/pingbiao`，API 前缀为 `/api/evaluation-workbench`。
- 使用独立 SQLite 数据库 `data/evaluation_workspace.db`。
- 文件位于 `data/evaluation_workspace/<project_id>/`。
- 不修改 `/bijiao`、`/api/compare` 的既有语义。
- 修改任何既有 API 路径、参数、字段、状态码、认证或跨域行为前，必须验证 `rokid_glasses_app` 兼容性。
- 项目删除会删除该项目数据库记录、上传文件、解析缓存和结果；仅在无运行/排队任务且用户确认后执行。

## 2. 不可违反的工程原则

### 2.1 固定优先级

**准确性与可追溯性 > 稳定性 > 效率 > Token 节省 > 展示便利性。**

性能优化不得减少全文覆盖、规则覆盖、关键证据页、异常恢复或人工可核验信息。无法证明不劣于基线的优化只能处于影子观测或默认关闭状态。

### 2.2 通用、治本、确定性优先

- 禁止将具体项目名、投标人、设备、金额、地区、页码、年份、错误句子写入生产判断逻辑或默认提示词。
- 禁止采用“发现一个错误，就追加一段提示词、一个正则或一个展示兜底”的方式持续修补。
- 修复前必须定位问题最早出现的层：文件解析、条款识别、来源单元映射、评分原文台账、证据定位、模型输出契约、证据合并、落库或展示。
- 能由本地确定性信息解决的事项，不交给模型猜测。典型包括文件哈希、规则 ID、条款 ID、页码、分值守恒、父子评分关系、启用状态、模型/提示词/代码版本和证据来源。
- 正则只允许承担结构识别、格式校验和候选召回，不得代替开放语义判断；词表只能是稳定的通用结构词或法律政策清单，不得随着案例增长。
- 模型负责理解语义、提出证据和建议；系统负责约束输入输出、保存来源、校验结构并显式暴露不确定性。

### 2.3 修复顺序

可靠性统一遵循：**校验 → 定向重试 → 显式标记 → 最后兜底**。

- 不允许格式异常后静默生成“看起来正常”的结论。
- 不允许一个规则组失败覆盖已经成功的规则组。
- 不允许历史风险结论、候选优先级或人工选择悄悄影响新一轮独立提取/评审。
- 兜底只能降低自动化程度，不得提高风险、分数或确定性。

### 2.4 小服务器约束

目标环境为腾讯云 2 核 2 GB：

- 禁止引入重型常驻服务和无界线程/进程池；
- 工作台空闲时不运行任务、不发模型请求，本地 OCR 懒加载并在空闲后回收；
- 本地 OCR 默认全局单执行位，模型请求仅在服务商限制内动态并行；
- 所有页数、字符数、图片像素、缓存、并发和重试必须有上限；
- 每个项目最多 12 份投标文件；单个 PDF 的解析、综合评审和查重页数上限统一为 2500 页，工作台单文件上传上限为 500 MB，独立三文件查重入口总页数上限为 7500 页。字符数、OCR/图片页数、缓存与并发仍使用各自独立上限，不能因页数放宽而同步无限放大；
- 新依赖必须同时验证 Docker 构建、峰值内存、Swap、冷启动和任务结束后的资源释放。

### 2.5 安全与兼容

- API Key、腾讯云密钥、Token、Cookie 和服务器凭据不得进入仓库、文档、日志和模型提示词。
- 密钥读取接口只返回“已配置”，不得回传明文或密文。
- 既有 API 优先向后兼容；新能力通过可选字段扩展，旧字段不得无提示改义。
- 历史结果保持可读；数据迁移优先新增字段、标记或适配，不静默覆盖。

### 2.6 变更分级与稳定核心保护

任何修改必须先分级，不能把业务口径变化伪装成普通修复：

| 变更级别 | 典型内容 | 开始前要求 | 文档要求 |
|---|---|---|---|
| A：业务决策 | 规则适用范围、评分含义、人工流程、默认选择 | 必须先获用户确认 | 必须更新对应基线 |
| B：核心架构 | 主流程、证据契约、缓存身份、OCR/模型路由、并发模型 | 先做方案、回退和 A/B 基线 | 必须更新架构与验收门槛 |
| C：兼容扩展 | 新增可选字段、服务商适配、报告格式 | 保持旧 API/数据可用 | 仅记录长期契约和兼容边界 |
| D：等价修复 | 不改变契约的代码错误、样式、日志、局部性能修正 | 定向测试和必要回归 | 通常不写本文档 |

第 3.4 节列出的稳定核心原则上不改动。确需调整时，必须说明“为什么现有核心无法满足需求、影响哪些契约、如何回退、用什么数据证明不衰减”，并在修改前更新方案、修改后更新实际状态。不得先改代码再用文档为结果背书。

### 2.7 变更闭环与评估资产

- 改动前先写清不变的业务契约、可复现样本、预期收益和可能退化的指标；不能只凭一次模型输出判断“修好了”。
- 一次修改应优先只改变一个责任层。若同时调整提示词、候选页、取证路由和结果合并，必须拆分为可独立回退、可比较的步骤。
- 用户已保存的模型、提示词、规则和历史结果不得被新默认值静默改写；任务应保留实际生效配置的版本/指纹，以便复现。
- 黄金项目和回归夹具是评估资产，不是针对某个项目写生产逻辑的理由。新增案例应抽象成可验证的通用性质，再进入测试。

## 3. 当前架构（已实施）

### 3.1 文件地图

- `dashboard/blueprints/evaluation_workbench.py`：页面与 API 边界、口令和请求校验。
- `dashboard/evaluation_workbench/storage.py`：SQLite、规则版本、任务、配置、缓存和结果持久化。
- `dashboard/evaluation_workbench/worker.py`：解析后任务、规则提取、全文扫描、综合评审、OCR/图片编排和结果归一化。
- `dashboard/evaluation_workbench/ai_gateway.py`：模型协议、请求、兼容响应和 Token 台账。
- `dashboard/evaluation_workbench/prompt_templates.py`：默认提示词及输出契约。
- `dashboard/evaluation_workbench/prompt_context.py`：提示词上下文构造。
- `dashboard/evaluation_workbench/collusion_signals.py`：查重候选与价值过滤。
- `dashboard/evaluation_workbench/ocr_gateway.py`：腾讯 OCR 能力适配。
- `dashboard/evaluation_workbench/local_ocr_gateway.py`、`rapidocr_worker.py`：RapidOCR 懒加载进程和资源回收。
- `dashboard/templates/evaluation_workbench/`、`dashboard/static/evaluation_workbench/`：独立前端和报告。
- `tests/test_evaluation_workbench.py`、`tests/test_evaluation_workbench_ai_gateway.py`：核心回归基线。

### 3.2 主工作流

1. 创建项目，上传招标文件、附件和多份投标文件。
2. 解析文件并按哈希保存页级文字与元数据。
3. 可运行多文件查重：本地生成低成本候选，AI 只复核压缩证据包。
4. 提取规则：结构定位 → 分段 AI 来源单元映射 → RC 否决条款台账与定向补提取 → 评分原文台账组装 → 疑似评分碎片定向重组 → 本地确定性收口 → 确定性校验。
5. 用户编辑、勾选并确认规则集。
6. 综合评审：项目范围画像 → 投标文件全文分块扫描 → 本地确定性证据补充 → 按策略分组审查/评分 → 必要 OCR/图片增强 → 证据合并 → 重要结论提炼。
7. 页面按投标人展示审查、客观分、主观分建议并导出报告。

### 3.3 任务与并发

- 使用 SQLite 任务队列和按需 worker，不引入 Redis/Celery。
- 跨项目任务按队列执行；等待项目应显示当前运行项目及其进度。
- 单任务内部可并行不同投标人、全文页块或模型规则组，但受任务级和服务商级闸门限制；限流或过载后自动降档。
- 本地 OCR 始终受独立全局执行位约束，不能随模型并发一起放大。
- 任务允许 `partial_success`：成功单元立即持久化，失败单元可定向重跑。
- 可恢复网络错误和 HTTP 5xx/429/529 只重试当前调用；4xx 配置错误不盲目重试。模型内容策略拒答属于不可重试的单元级失败：保留原文、隔离当前扫描块或规则组、继续其余单元并显式标记，禁止删改材料后重发同一请求。

### 3.4 受保护的稳定核心

下列设计经过多轮真实项目运行，是后续优化必须保护的基础。可以重构实现，但不得在没有等价验证和回退方案时改变其行为：

综合评审主链默认视为冻结：除非已经定位到明确的功能缺陷，或有真实运行数据证明存在显著的准确度、稳定性、耗时、Token 或资源收益，否则不得调整全文分块、规则分组、提示词顺序、证据上下文、思考模式、OCR/图片路由、并发或恢复策略。仅有理论收益、单次模型波动、局部缓存命中偏低或代码形式更整洁，均不足以启动主链修改；应先做只读诊断、影子观测和固定输入 A/B。当前生产回退版本及验收任务只记录在 `AI_HANDOFF.md`，避免本文随提交版本无限增长。

| 稳定核心 | 必须保持的行为 | 允许的优化边界 |
|---|---|---|
| 模块独立 | 独立页面、API、数据库和文件目录；不影响其他模块与外部调用方 | 内部拆分、索引和样式可改，外部契约保持兼容 |
| 按需任务 | 跨项目排队、空闲退出、2 核 2 GB 下无重型常驻服务 | 可优化调度和进度，但不得产生无界并发或空闲占用 |
| 全文覆盖 | 长文件从首页到末页扫描，失败页显式进入复核 | 可改分块、索引和缓存，不能以节省 Token 为由跳页 |
| 规则提取分层 | 结构定位、原子候选映射、评分原文台账组装、全局义务编译和确认前硬校验各司其职 | 可合并重复调用，不能删除来源追溯、评分守恒、子检查项和补漏校验；不得按规则数量切换不同业务语义 |
| 规则版本独立 | 新一轮普通 AI 规则独立重建；人工维护内容按稳定来源保留 | 可改善条款身份，不能继承旧 AI 勾选、风险或结论 |
| 证据先于结论 | 文字、OCR、图片和本地事实保留来源、页码、覆盖与冲突 | 可正式迁移到 EvidencePack，不能用字符串覆盖或展示层重算 |
| OCR 分层 | 文字优先、本地 OCR 按需基础取证、腾讯 OCR/多模态按规则增强 | 可换适配器和候选算法，不能让所有规则默认 OCR 或用未识别推断缺失 |
| AI 建议、人工裁决 | 系统给审查和评分建议，不产生法定串标、废标、最终分 | 可改善摘要和证据，不得提高系统决策权限 |
| 失败隔离 | 单调用重试、单规则组隔离、成功单元持久化、失败项可重跑 | 可优化恢复速度，不能因一个失败让长任务结果归零 |
| 严格复用 | 仅复用完整执行指纹一致的成功事实/结果；强制重跑真正绕过 | 可细化缓存层，不能跨代码、模型、提示词、规则或文件复用结论 |
| 提示词单一来源 | 可配置模板、稳定 ID、公共约束共享、结构契约明确 | 可精炼措辞，不能重复堆叠或依赖运行时替换修补 |
| 配置与结果可复现 | 每项任务保留实际生效的规则、模型、提示词和代码/解析指纹；更新全局配置不改写历史结果 | 可压缩快照和优化存储，不能丢失结果产生条件 |
| 可观测执行 | 页面和日志能区分阶段、重试、降级、部分成功、缓存命中及 OCR/图片实际处理范围 | 可优化日志和展示，不能把失败、回退或未覆盖静默伪装成成功 |
| 部署版本可信 | 页面蓝点与“模型用量·最后一次运行”共用任务运行时版本来源；镜像构建标记与部署记录保留为接口诊断和部署脚本校验 | 镜像标记存在但无效时必须显示 `unknown`，不得退回 Git/环境变量冒充版本；部署脚本不得在镜像、容器和部署记录不一致时报告成功 |
| 服务商无关 | 模型、腾讯 OCR、多模态差异停留在能力适配层 | 可新增服务商，业务规则不得出现服务商专属分支 |

判断是否“性能或功能不衰减”时，不能只看任务成功和页面能打开；至少同时比较规则召回、关键问题召回、错误高风险、建议分、证据页、失败恢复、总耗时、Token/OCR 调用和峰值资源。任一关键指标下降，默认回退原路径。

## 4. 规则体系与提取契约

### 4.1 规则类别与来源

类别为：资格性、符合性、实质性/废标、其他、客观分、主观分。页面将实质性和废标作为同类业务呈现，但保留历史类别兼容。

类别以招标原文的明确后果为准：原文明确载明无效、否决、取消资格或不得再参加采购的单文件审查事实，结构化决策影响为 `rejection`。当前优先由内部 `RC-*` 否决条款台账以稳定 `source_unit_ids` 与逐字后果短句挂接，规则元数据保存 `rejection_clause_ids`、完整紧凑台账和 `decision_impact_source=rc_ledger`；缺失、超出单次验证预算或校验失败时才兼容既有 `rejection` 类别及高精度原文后备。RC 只确认条款身份、触发条件、后果、例外、分包和原页，不判断投标人是否触发，也不构成系统自动废标。

来源为：

- `manual`：人工补充；
- `ai`：本轮 AI 提取；
- `ai_edited`：人工修改过检查内容或评分口径的 AI 规则；
- `global`：通用规则库。

展示顺序固定为人工补充/人工编辑、AI 提取、通用规则。页面以勾选启用为主，不提供常规删除入口；旧删除 API 仅为兼容保留。

### 4.2 重新提取

- 重新提取是全新运行：仅人工补充规则作为独立业务口径保留；旧 AI 提取/AI 编辑规则及其勾选、取证设置均删除。旧综合评审/评分/证据结果也删除，不继承、不展示、不复用；旧任务日志可保留用于运行诊断，但不作为业务结果。通用规则库按当前版本重新导入。
- 取证策略是本轮执行设置，不得把规则升级为 `ai_edited`；这样新一轮可按最新原文和证据要求重新规划取证，历史设置也不会制造规则副本。
- 模型附加的条款编号、分段编号或分值尾注不是规则对象。评分去重应先剥离这类机器尾注，再以对象、满分和同源原文合并；无法证明同一事实时保留并在确认前提示，不静默删除。
- “第 X 部分（X 分）”“商务/技术/服务部分（X 分）”等仅表达章节总分的文本是评分守恒台账，不是可执行评分规则；提取阶段应剔除，保留其下具备对象、条件、公式或分档的明细规则。
- 每个 AI 候选必须携带稳定来源：评分规则取自 `SC-*` 台账；非评分规则取自输入原文单元 `source_unit_ids`（文件、页码、自然段/表格行组），并明确 `verification_target`（当前文件中的具体核验对象）和 `verifiability`（仅允许 `single_bid`）。标题、检查语句、模型摘录、分段编号都不是来源身份；模型漏填单元时仅允许按直接摘录回填，不能按标题猜测。上述元数据必须随规则执行元数据落库，供审计和重跑比较。
- RC 台账候选只承担法律后果结构词的高召回；一次受约束模型调用只能引用输入 `source_unit_ids` 并逐字摘录后果短句，本地校验来源、最近分包标题范围、唯一 ID和否定语境。没有可靠来源或明确后果的条目不得升级为 RC；候选超出单次验证预算时显式跳过台账而非截断。RC 未被任何非评分规则承接时，只对该最小集合定向补提取，禁止重写整套规则集。`decision_impact` 的编译、全文扫描、OCR 和重点结论只消费这一统一身份结果。
- 主分段、资格补漏、硬性条款补漏和技术★兜底均须先经过同一候选契约和落库门控：非评分候选缺少来源单元、核验对象或 `single_bid` 范围时不得保存，任务结果必须记录排除数量。评分规则另按评分台账、满分和叶子结构收口。
- 非评分候选先做确定性同源去重，再进入全局“义务编译器”。编译器接收已过来源、分包和单文件门控的压缩候选清单；AI 只能返回每个候选恰好一次的 `merge/keep_separate` ID 分组，不能生成、删除或改写规则，不能触碰评分。代码负责合并原文、来源、取证要求和子检查项，并保存 `compiled_child_requirements`；最终综合评审仍逐项检查子项，只输出一条汇总结论。总范围与按章节、清单、模块、场景、分组或物项展开的同一“逐项响应/覆盖”检查必须汇总为一张卡；不同材料、字段、适用条件、独立证明要求或可分别成立的不响应事实必须分开。若模型返回合法、无交叉的 ID 分组但遗漏部分候选，已确认分组照常使用，遗漏项由代码以单条规则保留并计数；非法、交叉、越界、超安全上限、调用失败或格式异常时，先以同一受约束模板严格重试一次，仍失败则只保留确定性同源收口，不再将原始候选交给开放式语义去重。编译成功后仅对“同一材料主义务 + 表单/附件/填写细节”这一窄集合再做一次受约束 AI 裁决；本地只用连续身份片段建立候选索引，不直接合并，调用失败或拒绝合并时全部保留。两条路径均绝不静默丢规则。
- 评分后续只做“完整评分项原文 → 最终规则”的唯一归属组装。评分表的分部标题、总分、页脚、跨页档次续行、公式说明和证明材料只作为所属评分项上下文；“采用评分法、其中某部分 X 分、详见某章/细则”而没有实际计分对象、公式、分档、数量、材料或扣分条件的交叉引用属于导航说明，不得单独形成评分规则。分值构成摘要不得改变后续叶子条款所属分部；“技术评分”与“（40分）”分行时仍须识别为同一分部。导航与可执行细则的判断只信直接招标原文，不能因模型在 `check_rule`、`criterion` 中补写“公式”等文字而改变。评分表按同一文件的连续页面组装，不按不可靠的 PDF 分页或模型分类硬切分；下一页只有档次、扣分、公式尾部或材料说明而没有独立评分对象时，必须归入最近的具名评分项。每个 `SC-*` 可执行条款必须恰好归属一个最终评分规则。每组先只对遗漏条款补提一次，仍遗漏才对该小集合严格重试一次；原文明确总分且本地发现遗漏、重复归属或总分不守恒时，才对完整评分台账执行一次定向重组。仅当父项总分、子项和来源摘录均能在同一原文条款直接核验、且重组后恢复守恒时，才允许修正漏失的父子分值；重组仍异常时以任务结果和规则页提醒人工核对，但规则集可继续确认、修改、启停和执行；正常项目不增加这些调用。
- 正常链路使用义务编译器 V3：分段映射、评分/资格定向补漏完成后，非评分候选先形成完整原子台账，再由受约束的全局 ID 分组编译为页面规则；这不是全局自由改写。物理 `source_unit_ids` 仅表示位置，足够长的直接原文内容才可作为重复事实身份，防止同一评审要求在不同页重复成卡。历史项目数据不迁移、不删除；旧任务结果字段仅作向后兼容读取，不得重新接回旧流程。
- 评分原文是非评分提取的硬边界：候选的直接原文摘录若已属于 `SC-*` 评分台账，不得再生成 `other`、符合性或实质性规则；普通技术要求即使与评分表同页，只要摘录不属于评分条款，仍可按原规则提取。该边界由原文台账而非行业关键词判断。
- 页面不做空闲常驻轮询；项目可能被其他标签或会话更新时，在窗口重新获得焦点或进入评审规则页时按需刷新当前规则集，避免旧页面数据被误认成当前结果。
- 新草稿内可证明重复的评分副本应立即可逆停用；纯 AI 评分规则无法唯一挂接原文评分条款时，必须阻断确认，不得进入综合评分。
- 新增通用规则立即补入所有未确认项目；修改/删除通用规则不静默改写正在人工确认的项目。已确认项目通过重新提取获得最新通用规则。
- 通用规则全部导入项目，其“是否默认选择”只决定初始启用状态。

### 4.3 提取边界

- 只提取能从投标文件文字、表格、OCR 或图片事实中核验的要求；密封、递交、现场、纸质份数等文件外事实不得形成审查规则。评审小组从“有效性、完整性、响应程度”开展审查的概括性方法没有具体文件对象，不单独成规则；其下列明的签署、期限、报价、材料或参数等事实正常提取。缴纳、支付或提交保证金等文件外动作，只有原文明确要求投标/响应文件附凭证、保函、回单或证明材料时才形成文件内核验规则，不得由模型自行补造凭证要求。
- 条件性条款必须先确认当前采购包已启用，不得把模板条件句当成实际要求；直接原文已明确当前项目/采购包对应产品、服务、事项、材料或资格“无、不涉及、不适用”时，其后续条件要求不形成规则。项目明确排除某种参与方式时，只过滤以该方式的协议/资格材料为核验对象的条件模板；“禁止/不得采购”等仍可由投标文件核验的限制必须保留。投标人层面的“如有、若存在、如适用”等条件规则不静默删除：综合评审须先判定条件是否触发，未触发时写“条件未触发，无需提供”并给低风险，不得判缺失。平台上传/递交状态、加解密、提交时点、病毒扫描和文件系统完整性不属于当前系统证据能力；纯此类流程项不得成规则，混合条款只保留其中可由文件内容直接核验的部分。规则标题、核验对象和检查指令必须有直接来源支持，不得把表格/证书格式说明改写成另一业务对象。
- 多包招标必须先识别当前包范围，评分和技术参数不得跨包混入。
- 评分规则必须保留明确满分、计分对象、计分条件、上限和稳定来源条款 ID。每个可执行 `SC-*` 原文评分条款只能归属一个最终可执行评分规则；多个叶子可归入同一规则的 `scoring.items`。父项总分、跨页续行、公式说明只保留为台账上下文，不得成为可执行评分来源。只有本地能证明父项叶子完整覆盖子项时才自动收敛，否则保留全部证据并阻断确认。
- 评分表分部（价格/商务/服务/技术等）必须在原文解析时随叶子条款保存为 `score_sections`，并由最终评分规则继承；分部标题只接受完整的“部分/评审/评分 + 分值”结构，不能把“技术参数扣完 X 分”等具体评分条件误判为分部。分部合计对账优先使用该台账，禁止按 `source_page` 区间猜测归属。来源无法唯一匹配时不自动挂接，确认前必须以 `score_source_unmapped` 明示提示。
- ★技术参数只有同时存在实际标★叶子、实质性后果和证明材料要求时才形成受控规则；同一主题可合并展示，但独立叶子必须保存 `evidence_items`，不能共用一个模糊取证预算。
- 规则合并以同一评审事实为前提；资格门槛与评分、材料存在与材料得分、不同证明材料或不同计分叶子不得因标题相近合并。
- 规则数量由独立评审结论决定，而不是由对象名称、编号、列表层级、分组标题、位置描述或表格行等展示结构决定。同一连续需求只有在产生独立否决、独立评分或独立结论后果时才拆分；否则按当前采购包和连续主题形成少量 `other` 覆盖规则。具体原编号和叶子要求作为内部依据保留，综合评审仍逐项检索，页面默认不展开为大量规则卡片。
- 任何来源派生的补漏候选（包括技术★等）都必须在同一来源事实台账中进入去重、评分原文台账组装和确定性收口；禁止在落库前直接追加特殊规则。确认前校验发现来源、评分或覆盖问题时，只定向修复对应条款，不重新改写完整规则集。

### 4.4 确认规则集

确认前至少满足：

- 有一条启用规则；
- 启用评分规则具有大于 0 的满分；
- 无可确定的重复评分；
- 无同一 `SC-*` 评分条款被多个启用评分规则占用的归属冲突；
- 评分总分、评分条款覆盖和评分叶子结构异常会明确提示人工核对，但不阻断确认；同一评分原文被多条规则占用或 AI 评分规则完全无原文锚点时仍阻断确认，防止重复或无依据计分。

OCR/多模态能力不可用属于执行预警，不应与分值结构错误混为同一阻断条件。

## 5. 综合评审与证据契约

### 5.1 全文覆盖

- 长文件从第一页到最后一页按连续页块扫描，不为省 Token 跳页。
- 首轮只建立规则证据和项目范围偏离候选；最终结论按点状、数量累计、章节方案、全文一致性等策略分组生成。
- 每条规则必须获得自身的直接候选页；其他规则的高优先级证据不能挤掉它的唯一证据。
- 最终分组和输出预算必须同时计算规则卡、评分叶子、义务编译子项和证据子项，不能把一张复合卡误当成单点规则。复合规则先保留父规则直接证据，再在既有总上下文预算内按子检查项轮转候选页；未定位只表示本地未找到，不得写成投标人未提供，也不得为此增加全文扫描、OCR 页数或模型调用。首次有效判断保留模型既有思考能力；只有响应已触顶或违反结构契约后，才允许按事实型严格重试或拆小当前组，不能用全局关闭思考换速度。
- JSON 异常优先修复短响应或仅拆当前规则目录/规则组，不重复发送整份全文。
- 首轮失败页块必须在最终规则组携带原文或显式标记，不能静默丢页。

### 5.2 项目范围与内部一致性

- 项目范围画像仅来自招标文件和已确认规则；范围候选可以是无关主体、项目、地区、技术内容、设备、标准、服务对象、交付物或其他开放类型，不维护项目特例词表。
- 全文扫描的范围候选是本轮独立证据台账：同类重复可合并，不同开放类型须分别保留；在有限最终上下文中按类型轮转，并携带对应原页，不能由日期等单一高优先级类别挤掉其他类型。
- 业绩、资质、人员履历、注册地址、历史合同和合理规范引用不得仅因与当前项目不同而判异常。
- 历史模型的范围候选、风险或结论不得注入新一轮强制重跑。
- 固定响应表单的日期采用本地确定性候选：只读取偏离表、投标函、授权书、声明函、承诺函等直接“日期/落款/签署日期”字段邻域；标准编号、履历、合同、业绩、证照、出生和成立日期不进入。表单年份不一致或明显偏离招标时点时，只能写入明确要求日期/时点核验的规则，必须带入原页并降为人工复核，但不得自动判废。

### 5.3 结果结构

审查状态统一为：满足、不满足、部分满足、未找到证据、需 OCR、需人工判断。每条结果至少保存：

- 规则与规则版本；
- 投标人和文件；
- 关键证据、页码、理由和一句话结论；
- 风险、置信度、证据质量、覆盖状态及 `requirement_relation`（投标事实对规则要求的支持、直接相反或不确定）；
- OCR/多模态状态及分层证据；
- 模型、提示词、代码和输入指纹。

客观分、主观分只展示 `AI 建议得分`，不保存人工调整、有效分或最终分。建议分、计分过程和摘要必须一致；计分过程作为独立证据层，理由不重复规则和 OCR 全文。

扫描型文件或证据覆盖不足时，“未命中”既不等于缺失，也不等于满足。只有实际 OCR/图片证据完整覆盖后，才可恢复确定性结论或建议分；部分覆盖不得外推。

但 OCR 已读到与 `rejection` 规则直接相反的填写/声明文字时，应保留高风险和原页复核提示，不能仅因还需看图确认而降为低风险或从重点结论中消失；仍不得自动作出废标结论。

审查状态不得从理由中的“符合/满足/不符合”等自然语言反推或改写；尤其“符合禁止情形”属于直接相反事实。模型须输出 `requirement_relation`，代码只用该结构字段、规则决策影响和来源闭环收口状态；旧模板缺字段时按原始状态保守兼容。若明确否决规则的状态与显式关系冲突，不得自动放行或升级为直接反证，应保留原状态、将关系回落为不确定并要求人工复核。已确认的 `rejection + contradicts + 高风险` 候选必须进入重点结论候选池，摘要模型可压缩措辞但不得将其遗漏。

高风险、无效或否决候选还必须闭合到投标文件的可定位原文：模型不得凭名称近似、目录或概括补造填写值；本地发现关键填写值无法在已解析原文中复核时，只能显式降为待原页确认，不能保留确定性高风险。要求/响应数量不同是事实线索，不得仅因响应数量更多而推断虚假、无效或否决；只有规则原文明确要求相等、禁止正偏离、设置上限或规定该差异后果时，才可保留强负面结论。

后置 OCR/图片层写入或覆盖高风险事实后，必须对其实际证据页再做同页来源闭环：同页仍有足够机器可读原文且关键填写值无法对应时，回落为待原页确认；纯扫描页没有可比原文时保留图片事实与人工复核提示，不能因缺少解析文字而反向否定视觉证据。客观/主观建议分不得因这一收口被自动改分；只要计分理由、算式与已保存建议分冲突，就必须清除冲突计算文字并保留建议分与人工复核标记。

### 5.4 证据分层

当前结果由文字、RapidOCR、腾讯 OCR、多模态和本地确定性事实共同组成。任何后置层：

- 只能补充或纠正其实际覆盖的事实；
- 不得覆盖其他页已成立的全文事实；
- 发生冲突时并列展示并要求人工复核；
- 不得用字符串前缀或展示层正则冒充结构化来源；
- 对客观分只摘要材料、数量、有效性、页码、计分和未决项，不展示整段 OCR 转写。

OCR/图片证据层应同时保存其与规则的 `fact_relation`、不利影响等级、视觉依赖程度和规则决策影响；候选页、覆盖和结论只能消费这些结构化事实，不能从结果文本反向猜测。

`EvidencePack` 当前承担候选页来源、已核验页、证据层记录及只读的文档事实账本影子。事实账本每份投标文件只保存一次，仅记录有页码来源的通用表单字段和同一表格行内、列顺序明确的“要求/响应”数量对照候选；泛化陈述、跨行数字和普通技术数字不得形成候选。另可按同一材料键记录并列规则中“已定位证据/未定位”的相反既有观察，但它不推断材料缺失、不改变结论。两类影子信息均不参与提示词、选页、OCR、风险、建议分或最终结论；必须先完成召回与误报 A/B，才可接入跨规则一致性校验。正式迁移见第 10 节。

### 5.5 独立价格工作表

- “报价与价格分”位于评分结果之后；可在综合评审前独立使用，也会在综合评审结束后自动刷新本地报价并确定性试算。报价、参与范围和价格调整先在草稿中集中编辑，再通过一次批量保存统一重算；切换页面不丢弃未保存草稿。报价定位算法升级会递增识别指纹版本，历史报价台账自动进入刷新判定，避免沿用旧算法的空值或误识别。
- 文件查重和独立价格规则提取均可选择本次模型。查重将所选模型用于短证据包复核；价格页的“提取价格评分规则”只从评分原文台账定向组装价格规则，保存到独立价格规则台账，不覆盖完整规则集、不进入综合评审。完整规则集较新时优先使用其价格规则；用户随后主动独立提取时则以独立台账为准。
- 价格评分规则由该页面独立负责，综合评审与单独客观评分不再将其发送给模型，也不在“评分结果”重复展示。报价合规、最高限价、异常低价和其他非评分审查规则仍属于综合评审；历史价格评分结果保持可读但通过新增归属标记兼容隐藏。
- 价格工作表的 `GET` 必须纯读取：不得创建台账、提取报价或更新时间戳；仅在用户主动“重新识别”或前端检测到文件/解析指纹变化时发送明确的 `POST` 刷新，稳定打开页面不产生数据库写入。
- 已上传投标文件按文件哈希和解析结果缓存唯一总报价；只读取机器可读文字及已经存在的 OCR 页缓存，不为价格工作表启动 OCR、图片模型或文本模型。报价字段必须排除“报价表/报价栏/一览表”等章节标题；金额可位于明确报价字段之前或之后，但只取有限邻域中最近的金额；无单位金额仅作明确字段邻近的保守兜底，四位年份、日期和编号不得作为报价。存在多个不同金额或口径不明时必须留空并提示人工填写。
- 项目存在排队或运行中的任务时，价格工作表只返回缓存和人工数据，不扫描解析文件；任务结束后再自动刷新，避免与规则提取、综合评审争用 2 核 2 GB 服务器资源。
- 未上传文件的投标人可手工补录报价和计分价。计分价默认等于报价；人工可选择“价格优惠扣除”“剔除税率部分”或“直接填写计分价”，前两种由 `Decimal` 按明确的适用金额和比例确定性换算，复杂或叠加政策使用直接填写并备注依据。系统不得自行推断中小企业、本国产品或税率资格。
- 已上传投标人只能“移出价格试算”并可恢复，不能由价格表删除源文件或历史结果；没有上传文件的手工行可以删除。
- 当前规则明确属于价格评分且公式可确定性解析时，使用 `Decimal` 按全部参与人的计分价重算；任一“参与计算”的投标人缺少计分价时，系统不得以不完整样本生成基准价或自动价格分。公式可使用“高于/低于”或“每增加/每减少”表达价格偏离方向；暂不支持或要素不完整的公式只显示待人工核算，不提供逐投标人手工价格分输入，也不得由页面猜测公式。
- 同一项目存在多条价格评分规则时分别计算；规则草稿只能标为试算。规则、报价或参与范围改变后重新计算，但历史综合评审结果保持不变。

## 6. OCR 与多模态架构

### 6.1 能力分层

1. **全文机器可读文字**：默认、最低成本。
2. **本地 RapidOCR 基础层**：系统基础能力，但不是每条规则都执行；只在扫描型、文字不足、人工指定或决定性字段需要时处理有限候选页。
3. **腾讯 OCR 增强层**：可选，用于证照、证件、关键字段、低置信或本地识别不完整页；不可用时保留本地结果。
4. **多模态外观层**：可选，只用于签章、勾选、版式、照片、材料外观和其他视觉事实。

本地 OCR 与多模态相互独立；纯文字模型可以完成“全文 + 本地/腾讯 OCR 文字 + 结论”，非多模态模型不得因此阻断任务。

### 6.2 规则级策略

`baseline_ocr_mode`：

- `auto`：文字优先，证据不足或扫描型时有限 OCR；默认值。
- `text_only`：人工明确禁止 OCR。
- `local_ocr`：人工明确要求有限候选页本地 OCR。

增强核验只决定是否追加腾讯 OCR/多模态：不增强、智能增强、每次都增强。智能增强看证据缺口；每次都增强在已定位材料上仍执行一次。强度只控制页数和清晰度，不改变启动语义。

规则刚提取后的默认设置为低成本基础路径：全文文字优先，必要时最多调用本地 RapidOCR，不调用腾讯 OCR 或多模态。规则集工具条的“恢复默认（低成本）”必须恢复这一组字段；“采用 AI 建议（高计费）”才可按规则证据类型启用腾讯 OCR/多模态增强，并在执行前明确提示可能的按量费用。

“证书、报告、复印件、扫描件”只是材料名称或载体，不能单独导致每次 OCR。只有签章、勾选、手写、外观等必须看图的事实才强制视觉路径。

### 6.3 资源与兼容

- RapidOCR 懒启动，默认单进程/单执行位；允许短时复用引擎，但空闲后必须退出并释放流、进程和内存。
- OCR 页级缓存绑定文件哈希、页码、渲染和解析器版本；失败、空白、成功分开记录。
- 运行指标中的 `local_ocr_seconds` 只统计 RapidOCR 子进程实际推理耗时；渲染、排队、腾讯 OCR 与后续模型归纳另以流程墙钟指标记录，禁止混报为本地 OCR 性能。
- 综合评审任务结果可选 `performance_metrics` 仅记录模型分阶段墙钟、OCR/图片渲染、腾讯 OCR 与页级缓存计数；它不参与候选页、取证、风险、评分、复用或任何业务结论，供性能 A/B 定位使用。
- 综合评审任务结果可选 `evidence_context_shadow` 仅匿名汇总首次规则组实际携带的页块引用、全组件/同组件唯一页块与重复率及上下文字符量；不保留页码、正文或文件标识，也不参与规则分组、提示词、模型调用、OCR、缓存或任何业务结论。它只用于判断“页面中心化共享上下文”是否值得进入受控 A/B。
- 超大图片在渲染前受像素预算限制。
- 多模态通过能力适配层接入，不得在规则或评分业务代码中写入 MiniMax、腾讯或其他服务商特例。
- 保留历史 `image_mode`、`vision_trigger`、`vision_level`、`vision_status` 等字段兼容；新增状态只能扩展，不能让旧调用方失效。

## 7. 文件查重基线

- 本地负责候选召回和压缩，AI 负责对候选证据提出确认、疑似、排除或证据不足建议。
- 查重固定为**纯文字链路**：只读取 PDF 可提取文字，不调用本地 OCR、腾讯 OCR 或多模态图片识别。扫描比例只用于标注文字覆盖范围，不能作为异常证据，也不能把“未发现”表述为全文无异常。
- 不发送完整文件对；无候选不调用 AI；AI 失败时明确显示未完成并允许重跑。
- 证据必须显示双方投标人名称、各自页码和短原文，不使用无法辨认的 A/B 标签。
- 风险按高到低展示，不保存人工处置状态。
- 招标原文、公共表单和正常主体改写先过滤；表格换行、双栏错位和公共模板不得制造共同删除/共同错误。
- 联系电话、邮箱、姓名、身份证、地址只从明确字段提取；正文长数字不得猜成身份证。
- 每次结果必须保存查重链路指纹：比较器/信号规则版本、查重提示词指纹、模型公开配置、运行代码、部署版本与输入指纹。页面只能把指纹完全一致的结果标为“当前版本”；历史结果保持可读但必须提示重跑。
- AI 判定必须结构化标注来源属性（投标人特有、共同第三方资料、公共模板、占位/提取伪影、待核）及实质性。展示固定分为主线索、需结合背景复核的辅助线索、已排除或低价值线索三层；已排除项必入低价值层，实质性但存在公共/第三方合理解释的疑似项进入辅助层，后二者均不计入文件对复核优先级。
- 同一敏感实体或同一招标原文共同改动在三家以上投标文件中出现时，必须先按**单个原子事实**（一个实体值或一项“原文→改写”）建立项目级事实簇，只进行一次 AI 归属复核，再映射回各文件对。不得以一条信号的第一项证据代替其中其他实体或改动；出现次数本身不得抬高风险。正向 AI 结论必须同时给出理由和可执行核查建议，缺失时只重试该原子事实。AI 证据包最多三段，但应优先来自不同页对；共同改动须同时保留原文/改写，实体须保留字段语境。
- 系统只生成串标线索，不作法定串标认定，不自动废标。
- 修复误报必须处理对齐、来源分类或候选价值的根因，不得按某句话或某个行业模板加白名单。

## 8. 模型、提示词与全局规则

### 8.1 模型档案

- 模型档案是工作台级配置，不属于项目；可设置默认模型，项目默认选择随之变化。
- 支持禁用、删除和测试连接；禁用模型不出现在项目选择列表。
- API Key 可写入但永不回显。
- 纯文本与多模态能力由人工标记，图片调用前再次校验能力。
- DeepSeek、MiniMax 或未来模型的差异只放在协议/参数适配层，不进入评审规则代码。

### 8.2 提示词体系

右上角提示词配置按三组展示：

- **常用业务指令**：用户经常调整的判断口径和表达偏好；
- **业务流程细节**：规则提取、全文扫描、评审、评分、OCR/图片协作；
- **系统与结构模板**：JSON 契约、字段、恢复和系统边界，通常不应频繁修改。

所有运行提示词必须有唯一来源和稳定模板 ID。相同约束不得在多个模板重复堆叠；公共约束抽成共享片段。能通过业务提示词改善的语义判断优先修改提示词，但以下事项必须修改代码或数据契约：结构校验、分值守恒、缓存身份、页码来源、任务恢复、证据合并和 API 兼容。

修改提示词必须同步：默认模板、可配置展示、模板指纹、定向测试。不得用运行时 `.replace()` 隐式修补用户自定义提示词。

### 8.3 通用规则库

- 通用规则用于跨项目长期适用的评审事实，不用于存放某项目的资格、设备或评分细节。
- 新增规则立即同步所有未确认项目；修改/删除只影响规则库和后续提取，避免改写正在确认的项目。
- “是否默认选择”只决定初始启用状态，所有通用规则仍进入新规则集。
- 通用规则应写清启动前提、检查对象、证据、例外和输出要求；不得依赖模型自行猜适用范围。

## 9. 稳定性、缓存与验收

### 9.1 缓存身份

任何结果复用必须至少绑定：项目/文件哈希、规则集及启用状态、模型档案、提示词模板、解析/OCR版本、核心代码/部署版本和任务输入。`force_rerun=true` 必须绕过整任务、单文件和全文扫描的结果复用。

允许复用确定性事实和完全相同指纹的成功结果；禁止复用其他版本的模型结论、风险、候选优先级或失败兜底。

### 9.2 黄金项目

长期回归项目：

- 山西大学附属中学晋源学校教学设施设备采购项目教学仪器类采购；
- `sxyh`；
- 太原税务 2026 年府西办公区局域网升级改造。
- `cz`。

涉及规则提取、综合评审、OCR、多模态、查重或提示词的改动，必须选择适用项目进行 A/B，并检查：

1. 资格、★条款、评分和通用规则不丢失、不重复、不跨包；
2. 人工规则保留，普通 AI 勾选不继承；
3. 关键问题召回、错误高风险和建议分不劣于基线；
4. 证据页、OCR 页、图片页和最终理由一致；
5. 断连、限流、JSON 截断和单组失败可恢复；
6. 总耗时、模型调用、Token、OCR 页数和峰值资源有记录；
7. 相同输入连续三次不出现无法解释的结果漂移。

### 9.3 测试门槛

提交前至少执行：

```powershell
.\venv\Scripts\python.exe -m unittest tests.test_evaluation_workbench tests.test_evaluation_workbench_ai_gateway
git diff --check
```

改动前端时增加 JavaScript 语法检查和关键交互回归；改动 Docker/OCR 依赖时增加镜像构建与云端峰值资源检查；改动 API 时增加外部兼容验证。

## 10. 未来规划与启动门槛

### 10.1 第二阶段：正式 EvidencePack（计划中）

规则原子台账与义务编译已在 V3 落地：它保存来源、子检查项、评分归属和最终规则卡的关系。下一阶段只解决证据层，不再重做规则编译。

- `EvidencePack` 保存文字、OCR、腾讯 OCR、多模态事实、候选页来源、覆盖状态、冲突，以及当前已影子落库的规则关系/不利影响/视觉依赖元数据；文档事实账本先以只读影子保存通用字段和值差异候选，任何候选都不能绕过原页和语义确认直接改写结论。
- 子项级 OCR/图片收敛必须等 `EvidencePack` 能逐子项表达 `covered/missing` 后再启用；在此之前不得仅凭父规则的证据类型并集删减候选页，否则可能降低复合规则召回。
- 最终模型一次消费完整证据包，旧 API 由适配器渲染。
- 先以影子记录接入，再让候选页选择消费，最后只在一种高价值规则上 A/B 最终结论；禁止一次性重写主链。

启动条件：三个黄金项目连续三轮稳定；人工关键问题召回、建议分、错误高风险、失败率、耗时均有基线；存量结果和 `rokid_glasses_app` API 兼容测试通过。条件满足且用户讨论规则/证据架构时，应主动提醒可启动。

### 10.2 第三阶段：分层缓存与性能优化（计划中）

- 页文本缓存：文件哈希 + 解析器版本；
- 证据召回缓存：文件哈希 + RuleLedger 版本；
- 模型结论缓存：模型 + 提示词 + EvidencePack 哈希；
- 稳定文件摘要和提示词前缀重排仅做影子 A/B；
- OCR 批量归纳保持默认关闭，验证失败即回退逐条链路。
- 主观分中已声明 `cross_bid` 的规则可在全部单文件评分结束后生成横向影子对照；该开关默认关闭，影子分只写入任务运行元数据，不回写评分结果、不展示为正式建议分。只有三项目连续 A/B 证明与人工复核一致、且额外调用可控后，才可讨论进入正式评分链。

启动条件：EvidencePack 至少在一种规则上成为正式输入，且有数据证明缓存不会跨规则、提示词、模型或代码版本复用错误结论。

### 10.3 可选扩展

XLSX/DOCX 报告、更多 OCR/多模态服务商可按需扩展，但不得引入常驻重型依赖或改变现有 API。没有用户明确需求时不提前建设。
